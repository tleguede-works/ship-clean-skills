## 1. Résumé de la slice

F7 produit un **fichier PDF sur l'appareil**, sans réseau, lisible au format français, et
**l'empreinte imprimée dessus** (B10, `design-system.md` § 2 `EnTeteDevis`, slot
`empreinte`). Le rendu est local pour une raison qui n'est pas une préférence :
`prd.md` US-4 dit que le partage fonctionne sans réseau, et ADR-9 dit que l'export du
MVP ne peut pas avoir d'état d'erreur — ce qui n'est vrai que si le rendu est local.

Un PDF partagé ne devient **jamais** `envoyé par courriel` : rien ne confirme un partage
(B8). Cette impossibilité est aussi structurelle, côté serveur : `sortie_devis` interdit
qu'une ligne `pdf_partage` porte un `jeton`, et le `jeton` est la seule chose qui rattache
une sortie à une confirmation (§ 4.6).

**Vague 1** (`index.impl_waves[1]`). Dépend de `F1` et de `F5`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/sorties/montant.ts

import { z } from 'zod';

// Un montant est TOUJOURS en centimes entiers, et il entre par là.
// 0.1 + 0.2 n'est pas 0.3 : un flottant dans un document est un document faux.
export const Centimes = z.number().int().nonnegative();

// Le fichier produit. Il porte sa taille, donc un export « prêt » peut dire
// `2,4 Mo` sans jamais demander au serveur quoi que ce soit.
export const PdfProduit = z.object({
  octets: z.instanceof(Uint8Array),
  nomFichier: z.string().regex(/^atelier-devis-\d{4}-\d{2}-\d{2}\.pdf$/),
  taille_octets: z.number().int().nonnegative(),
});
export type PdfProduit = z.infer<typeof PdfProduit>;
```

### 2.2 Types et interfaces

```typescript
// apps/web/sorties/pdf.ts

export type PdfDevis = {
  rendre(d: DevisSignable, empreinteSignee: string): Promise<Uint8Array>;
};

export type PdfOptions = {
  // Les deux polices sont des OCTETS, pas des URL. Voir la raison en § 7.
  polices: Record<'texte' | 'identifiant', Uint8Array>;
};

// Les deux seules conversions du produit, et elles sont ici.
// `montantEnEuros` est la SEULE fonction qui produit une chaîne d'argent
// affichable ; l'écran, le PDF et l'export l'appellent tous les trois.
export function montantEnEuros(centimes: Centimes): string;      // 1440000 -> « 14 400,00 »
export function montantEnLettres(centimes: Centimes): string;   // -> « quatorze mille quatre cents »
```

### 2.3 Contrats API

Aucun : F7 ne parle à personne. Il produit des octets, et ce sont ces octets que
`S10` déclare à `F3` (`sortie_devis.date_declaree`) et que `S14` assemble.

**Une seule ligne de la § 5 est concernée**, et elle est écrite par `S10`, pas par F7 :
`sortie_devis.genre = 'pdf_partage'` avec `date_declaree` **et `jeton = NULL`**. Le `jeton`
nul n'est pas une valeur par défaut : c'est la contrainte `sortie_pdf_exige_date` du § 4.6
qui rend impossible une sortie à la fois confirmée et déclarée.

## 3. Algorithmes critiques

### `rendre` (couvre B3, B8, B10)

```
rendre(d, empreinteSignee):
  # 1. Le PDF porte le devis tel qu'il est SIGNÉ, c'est-à-dire le texte
  #    canonique porté par la signature — pas le devis du jour.
  #    C'est la seule forme qui rende le document opposable à un tiers.
  # 2. Aucune requête réseau. Les polices sont des octets déjà en mémoire.
  doc = PDFDocument.create()
  policeTexte  = await doc.embedFont(polices.texte, { subset: true })
  policeIdent  = await doc.embedFont(polices.identifiant, { subset: true })

  # 3. Le total vient de la MÊME expression que partout ailleurs (ADR-8),
  #    et il est imprimé deux fois : en chiffres tabulaires, et en toutes
  #    lettres. Les deux sortent de montantEnEuros / montantEnLettres.
  #    Jamais deux totaux DIFFÉRENTS : ils sont tous deux dérivés du même entier.

  # 4. L'empreinte, en bas, en police à chasse fixe.
  #    Elle est lisible sur le papier que le client emporte, pas seulement
  #    dans l'application : c'est le troisième endroit, et il n'y en a pas
  #    d'autre (§ 10.3).
  pied.ajouter(montantEnLettres(total), policeTexte)
  pied.ajouter(empreinteSignee, policeIdent)
```

### `montantEnEuros` (couvre B3)

```
montantEnEuros(c):
  # L'espace fine insécable du français, et la virgule décimale.
  # Aucun Intl, aucune locale : le rendu doit être identique sur l'appareil
  # et sur le serveur, comme l'empreinte. `toLocaleString` n'est pas ici.
  entier = c / 100 ; décimales = c % 100
  return groupéParMilliers(entier) + NAR + zéroOuNon(zéro) + virgule + deuxChiffres(décimales)
```

### `montantEnLettres` (couvre B3)

```
montantEnLettres(c):
  # « quatre mille huit cent soixante » : c'est la forme dont un artisan se
  # sert quand il annonce un prix à voix haute, et c'est une mention que la
  # loi prend au sérieux sur un devis.
  # Traitement : zéro → « zéro » ; 1 000 000 → « un million » ;
  # cent vingts → « cent vingt » (SANS s) ; quatre-vingts → « quatre-vingts » (AVEC s).
  # Les deux exceptions sont explicites dans le code et testées séparément :
  # elles sont la raison pour laquelle cette fonction est testée par propriété
  # et non par un jeu de cas.
```

### La propriété qui garantit qu'un montant ne varie pas

```
fc.assert(fc.property(fc.integer({min: 0, max: 99_999_999}), c => {
  const euros = montantEnEuros(c);
  return euros.includes(',')
      && euros.split(',')[1].length === 2
      && !euros.includes('.')
      && euros.replace(/[^0-9]/g, '') === String(Math.floor(c / 100)).padStart(1, '0');
}));
```

**Trois représentations, une seule source.** `montantEnEuros`, `montantEnLettres` et le
champ `total_centimes` de l'empreinte sortent tous du même entier. C'est la seule façon de
garantir qu'un montant ne varie pas entre l'écran, le PDF et l'empreinte (B3) : trois
formules libres donneraient trois réponses.

## 7. Pièges à éviter

- **Passer l'empreinte en paramètre depuis l'appelant comme une `Date`** — ⚠️ Ne pas
  recevoir une empreinte recalculée. Le comportement correct (ADR-6) est que le
  `Uint8Array` porte `signature_devis.empreinte`, celle qui a été signée, et l'appelant
  ne la recalcule pas.

- **Écrire `toLocaleString('fr-FR')`** — ⚠️ Ne pas formater un montant avec `Intl`. Le
  comportement correct (B3, `30-empreinte.md`) est `montantEnEuros`, écrit à la main :
  un formateur de langue varie selon la locale de la machine, et l'export serait différent
  sur un autre appareil.

- **Écrire un montant en flottant dans le PDF** — ⚠️ Ne pas faire `montant / 100` puis
  `toFixed(2)` au moment du rendu, deux fois dans deux endroits. Le comportement correct
  est de convertir **une seule fois**, en centimes, puis d'imprimer la chaîne.

- **Charger les polices depuis un CDN** — ⚠️ Ne pas écrire
  `await fetch('https://fonts.example/archivo.woff2')`. Le comportement correct (ADR-10,
  C11) est des octets same-origin : un CDN voit l'adresse IP de Jean-Luc à chaque
  ouverture, et `Cross-Origin-Embedder-Policy: require-corp` refuserait le chargement.

- **Imprimer `empreinte_courante`** — ⚠️ Ne pas inscrire l'empreinte du devis au moment
  du rendu si elle diffère de celle de la signature. Le comportement correct (B10) est
  l'empreinte **signée** : c'est elle qui atteste ce que le client a accepté, et c'est
  elle que la base revérifiera.

- **Ajouter un état d'erreur au `PanneauExport`** — ⚠️ Ne pas dessiner un état
  `echec` pour l'export. Le comportement correct (ADR-9) est que le design n'en dessine
  aucun, parce que l'export est local et n'a pas de phase qui puisse échouer seule.
  `dossier-client.md` et `reglages.md` citent pourtant un `PanneauExport` état `echec`
  qui n'existe pas dans l'union `EtatPanneauExport` : **c'est une divergence du design**,
  et le rapport de cette phase la signale. Tant qu'elle n'est pas arbitrée, le plan
  applique l'union du `design-system.md` § 2.
