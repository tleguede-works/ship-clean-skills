## 1. Résumé de la slice

F2 est **le seul endroit du dépôt où `Date.now()` et `new Date()` existent**, et elle
expose trois durées qui répondent à trois questions différentes : jusqu'à quand le prix
tient (`termeValidite`), quand la facture est due (`echeance`), quand relancer
(`jourRelance`). Les trois fonctions rendent **trois types de retour distincts**, et cette
distinction de types est ce qui rend la confusion impossible à écrire plutôt que
seulement discouraged.

Cette tranche est aussi, et c'est écrit dans `10-horloge.md`, **celle qui écrit
`eslint.config.js`**. Un fichier de config qui n'interdit rien n'est pas une règle en
attente : c'est un fichier qui laisse passer. Elle écrit donc, **dans la même tranche**,
`package.json`, `eslint.config.js`, `tsconfig.json`, `vitest.config.ts` et le premier
fichier de `packages/horloge/`, parce que le bloc d'exception
`files: ["packages/horloge/**/*.ts"]` ne résout sur aucun fichier tant que le paquet
n'existe pas.

**Vague 0** (`index.impl_waves[0]`). Les vingt sommets du graphe en dépendent
(`architecture.md` § 6.3) : c'est le sommet le plus universellement dépendu du projet.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// packages/horloge/src/durees.ts

import { z } from 'zod';

// B12 : « 15, 30 et 60 jours, 30 jours par défaut ». La liste est fermée,
// et Zod la refuse : une durée hors de la liste ne devient pas une durée.
export const DureeValiditeJours = z.union([z.literal(15), z.literal(30), z.literal(60)]);

// B18 : le délai de paiement est saisi par Jean-Luc (prd.md § 8 inconnues :
// « c'est une donnée de Jean-Luc, pas une décision de Forge »). Donc un entier
// strictement positif, et AUCUNE liste fermée : 30 jours est une valeur que le
// test fournit en imitant Jean-Luc, pas une constante du produit.
export const DelaiPaiementJours = z.number().int().positive().max(365);

// B20 : le jour de la relance n'est pas écrit nulle part (prd.md § 12).
// `DelaiRelanceJours` est donc déclaré mais **jamais alimenté** au MVP. Il
// existe pour que l'absence soit visible dans le code, pas dans un commentaire.
export const DelaiRelanceJours = z.number().int().positive();
export type DelaiRelanceJours = z.infer<typeof DelaiRelanceJours>;

// Une date « écrite sur le document » : `AAAA-MM-JJ`. Jamais un `Date`.
export const DateDocument = z.string().regex(/^\d{4}-\d{2}-\d{2}$/);
```

### 2.2 Types et interfaces

```typescript
// packages/horloge/src/index.ts

// Un instant, lu une fois. `dateFr` et `heureFr` sont **locaux** : c'est 18 h 12
// à Lyon, pas 18 h 12 UTC (architecture.md § 4.4, `heure_signee`).
export type Instant = {
  epochMs: number;
  dateFr: string;    // « 28 mars 2026 »
  heureFr: string;   // « 09:14:00 »
};

// Une source d'heure. Le test en fournit une ; la page en fournit une autre.
// Aucun autre module ne connaît l'une des deux.
export type SourceHorloge = { maintenant(): Instant };

// Trois résultats, trois types. Aucun « delai » générique n'existe dans ce
// paquet : c'est l'interdiction de roadmap.md § 5, rendue impossible par les
// types plutôt que conseillée par un commentaire.
export type DateLimite = { iso: string; joursRestants: number; depassee: boolean };
export type Echeance    = { iso: string; joursRetard: number;    depassee: boolean };

// Les trois durées ne se déduisent pas l'une de l'autre. `termeValidite` part
// de la date ÉCRITE sur le devis (B12, E15) ; `echeance` part de la date de la
// facture (B18) ; `jourRelance` part de l'échéance (B20).
export type Horloge = {
  maintenant(): Instant;
  termeValidite(d: { dateDocument: string; dureeValiditeJours: number }): DateLimite;
  echeance(f: { dateFacture: string; delaiPaiementJours: number }): Echeance;
  jourRelance(e: Echeance, delaiRelanceJours: number): DateLimite;
};

// La source de la source d'heure, c'est le paquet. `10-horloge.md` interdit
// « une variable de module qui stocke l'heure » : donc `horloge()` PREND la
// source, et il n'existe aucun `maintenant` global mutable.
export function horloge(s: SourceHorloge): Horloge;

// Le SEUL endroit du dépôt qui appelle `Date.now()`. C'est ici, et nulle part
// ailleurs, que `page.clock.install()` aura prise.
export function sourceSysteme(): SourceHorloge;

// L'horloge du produit, bâtie sur la source système. `const` et non `let` :
// elle ne change pas de source en cours de vie.
export const horlogeSysteme: Horloge = horloge(sourceSysteme());
```

### 2.3 Contrats API

Aucun : F2 ne parle à personne. Le serveur a sa propre horloge, et elle est **visible
dans le schéma** : `signature_devis.recu_le`, `envoi_courriel.demande_le`,
`facture.emise_le` portent le `DEFAULT now()` de PostgreSQL. Ce sont deux horloges
délibérément distinctes (R-04), et les garder séparées est la mesure qui rend l'écart
visible dans l'archive au lieu de le faire disparaître.

## 3. Algorithmes critiques

### `termeValidite` (couvre B12, E15)

```
termeValidite(d):
  assert DureeValiditeJours.parse(d.dureeValiditeJours)      # 15 | 30 | 60, sinon refus
  terme = d.dateDocument + d.dureeValiditeJours jours        # arithmétique de dates, pas de fuseau
  jours = nombre de jours entre la date du jour et terme
    jours > 0 → DateLimite { iso: terme, joursRestants: jours, depassee: false }
    jours = 0 → DateLimite { iso: terme, joursRestants: 0,  depassee: false }   # le jour du terme, le prix tient
    jours < 0 → DateLimite { iso: terme, joursRestants: jours, depassee: true  }
```

**La date de départ est `date_document`, jamais « aujourd'hui ».** Un devis écrit le
28 mars et envoyé le 18 avril expire le 27 avril, pas le 17 mai : c'est E15, et c'est la
raison pour laquelle la fonction ne prend aucun paramètre « maintenant » séparé.

### `echeance` (couvre B18)

```
echeance(f):
  assert DelaiPaiementJours.parse(f.delaiPaiementJours)      # entier > 0, liste ouverte
  limite = f.dateFacture + f.delaiPaiementJours jours
  retard = nombre de jours entre la date du jour et limite, signé
  → Echeance { iso: limite, joursRetard: max(retard, 0), depassee: retard < 0 }
```

### `jourRelance` (couvre B20 — non instantiated au MVP)

```
jourRelance(e, p):
  assert DelaiRelanceJours.parse(p)
  → DateLimite { iso: e.iso + p jours, … }
```

**`p` n'est jamais fourni au MVP.** `configuration.delai_relance_jours` reste absent tant
que `prd.md` § 12 n'est pas tranché, donc la fonction est écrite et testée par
propriété, mais **aucune tranche ne l'appelle**. Elle existe pour que la V1 n'ait pas à
inventer une quatrième durée en même temps qu'elle écrit `S20`.

### La propriété qui prouve que les trois durées ne se confondent pas

C'est une propriété **nulle**, et elle est le cœur du paquet :

```
pour toute date j et tout délai p :
  echeance({ dateFacture: j, delaiPaiementJours: p }).iso
    ≠ termeValidite({ dateDocument: j, dureeValiditeJours: d }).iso
  dès que p ≠ d  (d ∈ {15, 30, 60}, p entier positif)
```

Écrite en fast-check :

```typescript
fc.assert(fc.property(
  fc.date({ min: new Date('2026-01-01'), max: new Date('2027-12-31') }),
  fc.integer({ min: 1, max: 365 }),
  fc.constantFrom(15, 30, 60),
  (j, p, d) => {
    const jIso = j.toISOString().slice(0, 10);
    const e = h.echeance({ dateFacture: jIso, delaiPaiementJours: p });
    const t = h.termeValidite({ dateDocument: jIso, dureeValiditeJours: d });
    return p === d || e.iso !== t.iso;
  }
));
```

## 7. Pièges à éviter

- **Écrire `eslint.config.js` sans créer `packages/horloge/`** — ⚠️ Ne pas livrer la
  tranche avec le seul fichier de config. Le comportement correct (`10-horloge.md` §
  « La configuration qui rend la règle applicable ») est deux blocs dans un ordre précis :
  l'interdiction d'abord, l'exception **après**. Sans second bloc, l'exception n'est pas
  prouvée ; sans fichier dans `packages/horloge/`, elle ne porte sur rien.

- **Ajouter une variable d'heure au niveau module** — ⚠️ Ne pas écrire
  `let sourceCourante = sourceSysteme()` pour éviter de passer la source en argument.
  Le comportement correct (`10-horloge.md` § Motifs interdits) est une source **injectée** :
  « la source d'une source d'heure, c'est le paquet ».

- **Ajouter une quatrième durée** — ⚠️ Ne pas créer un `delaiJours(d)` générique « pour
 factoriser ». Le comportement correct (`roadmap.md` § 5, ADR-5) est trois fonctions et
  trois types de retour : un délai unique produirait soit des devis expirés avant leur
  échéance, soit des relances envoyées avant que la facture soit due.

- **Faire de `echeance` une fonction de `termeValidite`** — ⚠️ Ne pas écrire
  `termeValidite(...) - delaiPaiementJours`. Le comportement correct (`10-horloge.md` §
  « Quand écrire du code qui parle de temps ») est que les types de retour distincts
  rendent cette expression impossible à écrire, pas seulement discouraged.

- **Utiliser `Date.parse` sur une date locale** — ⚠️ Ne pas écrire `new Date('2026-03-28')`
  pour l'arithmétique. Le comportement correct est une arithmétique de **dates civiles**,
  en UTC sur des chaînes `AAAA-MM-JJ` : une heure d'été ne doit pas faire perdre un jour
  de validité.
