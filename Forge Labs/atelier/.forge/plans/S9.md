## 1. Résumé de la slice

S9 dit honnêtement **où en est un envoi parti**, et fait baisser le compteur au moment
**exact** où le service confirme. L'état `attente` est l'état le plus important du produit
et le plus difficile à instrumenter : il affiche **ni pourcentage, ni spinner, ni
`Réessayer`**, parce que rien n'a échoué et que B7 interdit le doublon. Il affiche un fait
et une promesse : `N devis attendent la confirmation` et `repartiraient seuls`.

**Vague 9** (`index.impl_waves[9]`), sur le chemin critique de la sortie. Dépend de `F1`,
`F2`, `F4`, `F6`, `F8`, `S8`.

### 2.2 Types et interfaces

```typescript
// apps/web/sorties/surveillance.ts

export type Surveillant = {
  // Le client INTERROGE, il ne boucle pas. Cette fonction est appelée quand
  // l'application est ouverte et quand le réseau revient — jamais sur un
  // `setTimeout`. `20-ecriture-locale.md` : « il n'y a aucun délai actif ».
  interroger(): Promise<void>;

export type BandeauEtat = 'attente' | 'vide' | 'impossible';
```

### 2.3 Contrats API

`GET /api/v1/envois/:jeton` (§ 5.5), en lecture seule. Un `404` est une **réponse** et
non une erreur : le serveur n'a jamais reçu la tentative, donc aucun courriel n'est parti,
donc Jean-Luc peut réessayer **avec le même jeton** sans risque de doublon.

## 3. Algorithmes critiques

### `confirmerOuConstater` (couvre B6, B23, E3)

```
confirmerOuConstater(jeton, service):
  # Le client ne fait QU'UNE requête par entrée en attente. Il n'en fait pas
  # deux « pour être sûr », parce que la deuxième serait une occasion de
  # déclencher un doublon dans un service mal écrit.
  r = await service.interroger(jeton)                       # ← GET, une seule fois

  cas r :
    Confirmation{ etat: 'confirme', confirme_le, adresse } →
        F3.dansTransaction(tx ⇒
            UPDATE envoi_courriel SET confirme_le = …        # sur le serveur
            UPDATE devis SET sync_etat = 'envoyé'
            F4.marquerConfirme(jeton)
        )
        F8.compteurNonEnvoyes = compteurNonEnvoyes - 1       # ICI, pas avant
        F8.fichierEnAttente  = fichierEnAttente - 1         # ET ICI
        # La ligne quitte le groupe 1 de S2 pour le groupe 2, au même instant.
        bandeau → 'attente' s'il reste des entrées, sinon 'vide'

    Confirmation{ etat: 'refuse', motif, reessayable } →
        F4.marquerEchoue(jeton, motif)                       # le MOTIF, jamais « échec »
        devis.sync_etat reste 'écrit ici, pas encore envoyé'  # B6
        bandeau → 'impossible'                               # c'est le seul cas

    'inconnu' (404) →
        # § 5.5 : aucun courriel n'est parti. Jean-Luc peut réessayer avec
        # LE MÊME JETON, sans risque de doublon.
        entrée reste 'en_attente'
        bandeau → 'impossible'                               # réseau ou service muet

    erreur réseau →
        entrée reste 'en_attente'                            # rien n'est écrit
        bandeau → 'impossible'
```

### `bandeau` (couvre R-06, B23)

```
bandeau(fichierEnAttente, fichierImpossible, enLigne):
  # L'ORDRE COMPTE : « impossible » passe avant « attente ».
  si fichierImpossible                        → 'impossible'
       « Le service de courriel ne répond pas. Les N devis attendront, et
         repartiront seuls. »  +  bouton `Réessayer maintenant`
  sinon si fichierEnAttente > 0                → 'attente'
       « N devis attendent la confirmation du service de courriel. »
       AUCUN bouton. AUCUN pourcentage. AUCUN spinner. AUCUN point animé.
  sinon                                       → 'vide'
       # Le bandeau N'EXISTE PAS. Un état vide n'est pas un « 0 sur 0 »,
       # et une liste vide ne doit pas ressembler à une panne (B26).
```

**Le bandeau ne devient jamais `impossible` parce que le réseau manque depuis un moment.**
Il devient `impossible` quand **le service n'a pas répondu**. Ce sont deux faits, et les
deux ont leur place : `1b` sur la preuve du devis pour le réseau, `impossible` sur le
bandeau pour le service.

### `quandInterroger` (couvre B7, E3 — ce qui n'est PAS fait)

```
quandInterroger():
  # Trois déclencheurs, et RIEN D'AUTRE :
  #   1. l'ouverture de l'application
  #   2. l'événement `online` du navigateur
  #   3. l'action explicite de Jean-Luc (`Réessayer maintenant`)
  #
  # Ce qui n'est PAS fait, et c'est la règle :
  #   * aucun `setTimeout` d'attente active
  #   * aucune `setInterval`
  #   * aucune boucle while
  #   * aucun `retry` dans le client HTTP
  #   * aucun second envoi pour « être sûr »
  #
  # Raison : Jean-Luc doit pouvoir poser le téléphone. Une attente active est
  # une attente à laquelle il ne peut pas échapper, et une boucle qui
  # interroge deux fois peut créer un doublon dans un service mal écrit.
```

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `confirme_le` | serveur | `envoi_courriel` (`architecture.md` § 4.5) | horloge serveur | une seule fois, **jamais retirée** — garde `G5` |
| `sync_etat` du devis | appareil | `devis.sync_etat` | `écrit ici` | à la confirmation |
| Entrée de file | appareil | `F4` | à `F4.entrer` | à `confirme`, `echoue`, `invalide` |
| `fichierEnAttente` | globale | `F8` | au démarrage | à chaque confirmation ou échec |
| `fichierImpossible` | globale | `F8` | `false` | à un refus, à un `404`, à une erreur réseau |
| Déclencheurs d'interrogation | page | `abonner()` sur trois événements | à l'ouverture | jamais — ce n'est pas une liste |

**`confirme_le` est monotone et ne revient jamais à `NULL`** : le déclencheur
`envoi_confirmation_monotone` (§ 4.14) le refuse, et la garde `G5` le prouve. Sans cela, un
devis pourrait repasser de `envoyé par courriel` à `écrit ici, pas encore envoyé` alors que
le client a le document — et B6, la règle centrale du produit, cesserait de tenir.

## 7. Pièges à éviter

- **Mettre un pourcentage ou une durée estimée dans le bandeau** — ⚠️ Ne pas écrire
  `67 %` ni `dans 2 minutes`. Le comportement correct (R-06, `design-system.md` § 6) est
  que le produit **ne sait pas** combien de temps il lui reste : afficher un pourcentage
  serait exactement le mensonge que ce produit a été conçu pour ne pas produire.

- **Mettre un spinner ou un point animé dans le bandeau** — ⚠️ Ne pas. Le comportement
  correct est un bandeau **immobile** : il contient un fait et une promesse, et une
  animation invite à attendre là où Jean-Luc a un client à servir.

- **Proposer `Réessayer` sur un devis en attente** — ⚠️ Ne pas. Le comportement correct
  (B7) est que `Réessayer` n'apparaît **que** à l'état `impossible` du bandeau — c'est-à-dire
  après qu'on **sait** que ça ne marche pas.

- **Faire une boucle d'interrogation** — ⚠️ Ne pas écrire
  `setInterval(() => interroger(), 5000)` ni `while (!confirme) await interrogate()`. Le
  comportement correct (`20-ecriture-locale.md`) est que le client **interroge** : trois
  déclencheurs — ouverture, `online`, action de Jean-Luc — et **aucun délai actif**.
  `grep -rn 'setInterval\|setTimeout' apps/web/sorties/` doit rendre **0**.

- **Retirer une confirmation** — ⚠️ Ne pas remettre `confirme_le` à `NULL`. Le
  comportement correct (`G5`) est qu'elle **ne se retire pas** : le bandeau ne propose
  `Réessayer` qu'à l'état `impossible`, donc un état `impossible` doit être inatteignable
  pour un devis confirmé.

- **Rendre le bandeau « vide » avec un `0 sur 0` ou un tick vert** — ⚠️ Ne pas. Le
  comportement correct est que **le bandeau n'existe pas** : un état vide n'est pas un
  `0 sur 0`, et une icône de victoire serait une conversation sur un fait qui n'a pas
  d'enjeu.

- **Faire baisser le compteur à l'envoi tenté** — ⚠️ Ne pas. Le comportement correct (B6,
  B23) est qu'il baisse **à la confirmation**. Un compteur qui baisse quand la requête
  part dit à Jean-Luc qu'il n'a plus rien, et qu'il n'a peut-être rien envoyé.
