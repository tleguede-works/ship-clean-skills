## 1. Résumé de la slice

S12 réunit **tous les devis et toutes les factures** d'un client, en séparant ce qui est
parti de ce qui ne l'est pas, avec son adresse de facturation **modifiable une seule fois**.
C'est le réceptacle du module Dossier, dont l'export (B24, porté par `S14`) est la raison
d'être dans le MVP.

Deux clients du même nom sont listés avec leur adresse complète et **aucun n'est
présélectionné** : confondre deux dossiers, c'est envoyer un devis au mauvais client. Et
**la facturation n'a pas de groupe tant qu'il n'y a pas de facture** — un groupe vide
« Factures » ferait croire à un manquant.

**Vague 7** (`index.impl_waves[7]`). Dépend de `F1`, `F2`, `F3`, `F8`, `S6`, `S11`. Peut
être parallélisée avec `S7`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/app/dossier-client/types.ts
import { z } from 'zod';

// E12 : l'adresse de facturation est celle du dossier. Jean-Luc la modifie
// ICI, et UNE SEULE FOIS. Le schéma rend donc l'absence d'adresse visible
// plutôt que tolérée : `client.adresse` est `NOT NULL` dans le § 4.1, donc
// un dossier sans adresse porte une chaîne vide, ce qui est un fait
// distinct de « aucune donnée ».
export const AdresseFacturation = z.object({
  client_id: z.string().uuid(),
  adresse: z.string().min(1, {
    message: 'Écrivez l\'adresse de facturation.' }),
});
```

### 2.2 Types et interfaces

```typescript
// apps/web/app/dossier-client/vue.ts

export type DossierClient = {
  client: Client;
  // E12 : l'adresse est celle du dossier, et c'est ici qu'elle se modifie.
  adresse: z.infer<typeof AdresseFacturation>['adresse'];

  // Les deux groupes, TOUJOURS PRÉSENTS, comme sur `suivi` (B26).
  nonEnvoyes: LigneListe[];
  partis: LigneListe[];

  // Le compteur, exact, comme partout ailleurs (B23).
  compteurNonEnvoyes: number;

  // Le groupe « Factures » n'existe PAS tant qu'il n'y a pas de facture.
  // Au MVP il n'y en a JAMAIS (roadmap § 2.2), donc ce champ vaut toujours
  // `null` ici — et il est déclaré pour que S18 n'ait pas à modifier l'écran.
  factures: LigneListe[] | null;   // null = aucune facture, donc pas de groupe
};

// E12 : une seule fois. Ce drapeau est local au dossier et vit le temps de
// l'écran : c'est une interaction, pas un fait de base.
export type EditionAdresse = { enCours: boolean; dejaEcrit: boolean };
```

Aucun : le dossier est **entièrement local**, et l'export aussi. `dossier-client.md` § 4 le
dit de l'export : « il produit un fichier sur l'appareil, il ne contacte personne ».

## 3. Algorithmes critiques

### `repartirDossier` (couvre B21)

```
repartirDossier(client_id, sourceF2):
  # Deux tableaux, TOUJOURS deux tableaux. Un tableau qui n'existe pas quand il
  # est vide fait de la perte une absence ; deux tableaux vides font de la
  # perte un fait visible.
  nonEnvoyes = []
  partis     = []

  pour d dans SELECT * FROM devis WHERE client_id = … :
      ligne = { numero, date_document,
                etatSortie, preuve, signatureEtat,
                terme: F2.termeValidite({ dateDocument: d.date_document,
                                          dureeValiditeJours: d.duree_validite_jours }),
                nb: 1 + (SELECT count(*) FROM ligne_devis WHERE devis_numero = d.numero) }

      SI d.sync_etat == 'écrit ici' ET la validité n'est pas dépassée :
          nonEnvoyes.push(ligne)
      SINON :
          partis.push(ligne)

  # Les factures : NULL au MVP. Pas un tableau vide — un tableau vide
  # s'afficherait avec un compte 0 et une phrase « aucun devis n'est encore
  # parti vers ce client », ce qui ferait croire à un manquant.
  factures = (SELECT count(*) FROM facture WHERE client_id = …) > 0
           ? … : null

  trier nonEnvoyes par rang DESCendant   # l'ordre de production inverse : le
                                         # plus récent en haut. Pas par heure
                                         # de sortie : c'est un ordre de
                                         # DÉPART, pas de consultation.
  trier partis     par date_document décroissante
```

### `modifierAdresseUneFois` (couvre E12)

```
modifierAdresseUneFois(client_id, adresse, dejaEcrit):
  SI dejaEcrit :
      renvoyer { refus: 'L\'adresse de facturation de ce dossier est déjà écrite.
                          Un nouveau document porte la version à jour ; elle ne se
                          réécrit pas.' }
  SINON :
      F3.dansTransaction(tx ⇒ UPDATE client SET adresse = …)
      # Les devis et factures DÉJÀ ÉMIS conservent l'adresse qu'ils portaient :
      # un document parti ne se réécrit pas (B19 pour une facture, et le même
      # raisonnement pour un devis sorti). « Les documents suivants utilisent
      # la version à jour » — suivants, pas présents.
      return { ok: adresse }
```

**Le refus est une phrase, pas une erreur technique**, et il dit ce que la règle veut :
l'adresse est **unique** dans la vie d'un dossier. Une nouvelle adresse pour un client qui
a changé de domicile est un **nouveau dossier**, et c'est une décision à demander à
Jean-Luc, pas une secondation.

### `etatExportDansDossier` (couvre B24, ADR-9)

```
# Le PanneauExport est dans le dossier, et son échec est DANS LE PANNEAU —
# pas dans le dossier. Un export échoué ne cache pas l'original : c'est une
# copie, et l'échec d'une copie n'a pas de raison de cacher la chose copiée.
#
# `design-system.md` § 2 PanneauExport ne dessine QUE trois états :
# inactif, preparation, pret — et AUCUN état d'erreur, parce que le rendu est
# local et n'a pas de phase qui puisse échouer seule.
#
# `dossier-client.md` § 4 et `reglages.md` § 4 citent pourtant un
# « PanneauExport état echec » qui n'existe pas dans l'union
# `EtatPanneauExport`. C'est une divergence du design ; ce plan applique
# l'union du § 2, et le rapport de la phase la signale.
```

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `dossier` | page | état local, alimenté par une lecture `F3` | au montage | à l'envoi d'un devis, à l'export |
| `adresse.dejaEcrit` | page | état local | `false` | après un enregistrement réussi |

| `client.adresse` | appareil | `F3`, table `client` | à la création du dossier | **une seule fois**, par ce formulaire |

**`adresse.dejaEcrit` n'est pas un fait de base.** C'est une interaction d'écran : Jean-Luc
l'a écrite une fois dans cette session. Si l'écran se rouvre, la règle doit rester
applicable : la règle est donc portée par `client.adresse != ''` **et** par le drapeau
local, ce qui rend la refus Impossible à contourner en rechargeant.

## 7. Pièges à éviter

- **Afficher un groupe « Factures » vide** — ⚠️ Ne pas. Le comportement correct
  (`design-system.md` § 2 `FicheClient`) est que la facturation **n'a pas de groupe tant
  qu'il n'y a pas de facture** : un groupe vide ferait croire à un manquant. Le champ est
  `null`, pas `[]`.

- **Laisser modifier l'adresse d'un dossier une deuxième fois** — ⚠️ Ne pas. Le
  comportement correct (E12) est qu'elle est modifiable **une seule fois** ; un changement
  de domicile est un **nouveau dossier**, et c'est une décision à demander à Jean-Luc.

- **Réécrire l'adresse sur des devis déjà sortis** — ⚠️ Ne pas. Le comportement correct est
  que les documents **présents** gardent l'adresse qu'ils portaient et que les
  **suivants** utilisent la version à jour. Un document parti ne se réécrit pas.

- **Vider le dossier quand le magasin ne répond pas** — ⚠️ Ne pas rendre une liste vide.
  Le comportement correct est de **garder le contenu affiché** et d'ajouter un bandeau
  : une liste vide pour un dossier illisible ferait croire que M. Roux n'a jamais eu de
  devis ici.

- **Mettre l'échec de l'export dans le dossier** — ⚠️ Ne pas. Le comportement correct est
  que l'échec est **dans le `PanneauExport`** : l'export est une copie, et l'échec d'une
  copie n'a pas de raison de cacher l'original.

- **Ajouter un état d'erreur à `PanneauExport`** — ⚠️ Ne pas. Le `design-system.md` § 2 en
  dessine trois et **aucun** d'erreur, parce que le rendu est local et n'a pas de phase
  qui puisse échouer seule (ADR-9). Le § 4 de `dossier-client.md` et de `reglages.md` en
  cite pourtant un : c'est une divergence du design, signalée, et ce plan applique l'union
  du § 2.

- **Trier par heure de sortie** — ⚠️ Ne pas. Le comportement correct est la **date
  écrite** du document, du plus récent au plus ancien : l'heure de sortie est un ordre de
  départ, cette liste est un ordre de production.

- **Proposer une modification sur une ligne signée** — ⚠️ Ne pas. Le comportement correct
  est que le document signé est figé, et que le dossier ne propose rien qui le déferait.
  L'adresse, elle, n'est pas une partie du devis.

## 10. Critères d'acceptation

- [ ] B21 : propriété fast-check — la somme des deux groupes vaut le nombre de devis du dossier, sans doublon.
- [ ] E12 : l'adresse de facturation est modifiable **une seule fois**, et le refus tient après un rechargement ; les devis déjà écrits gardent leur adresse, les suivants portent la nouvelle.
- [ ] E14 : deux devis du même client le même jour apparaissent dans le même dossier, avec deux numéros distincts.
- [ ] `design-system.md` § 2 `FicheClient` : le groupe « Factures » est **absent** tant qu'il n'y a pas de facture, et le champ vaut `null`, pas `[]`.
- [ ] C1 : hors ligne, aucun bandeau n'apparaît et le dossier est identique ; `grep -rn 'fetch' apps/web/app/dossier-client/` rend 0.
- [ ] ADR-9 : l'échec de l'export est porté par `PanneauExport` et **jamais** par le dossier, qui reste intégralement lisible.
- [ ] Un devis signé n'offre **aucune** action de modification dans le dossier.
