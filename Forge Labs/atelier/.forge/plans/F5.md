## 1. Résumé de la slice

F5 transforme un devis en **une suite d'octets unique**, et sait la relire deux fois :
une fois dans le navigateur au moment de la signature, une fois par PostgreSQL à la
réception. C'est la seule garantie juridique du produit — `contract.md` § 3 achète une
signature tracée à 0 € et exclut la qualifiée à 1–3 € — donc le paquet est petit et
n'a **aucune dépendance** en dehors de l'API Web Crypto.

Le paquet est **unique et importé des deux côtés**. C'est la raison pour laquelle il est
un paquet et non un dossier, et c'est la seule réponse au risque numéro un du projet :
deux implémentations du texte canonique produisent deux octets possibles, et l'empreinte
vérifiée n'est alors plus celle qui a été signée.

**Vague 0** (`index.impl_waves[0]`). Dépend de rien. Dépendue par `F3`, `F4`, `F6`,
`F7`, `S6`, `S7`, `S10`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// packages/empreinte/src/type-devis.ts

import { z } from 'zod';

// `DevisSignable` n'est PAS un schéma de persistance : c'est la projection
// minimale dont le texte canonique se déduit. Un champ de plus change
// l'empreinte, donc un champ de plus ici est un changement de signature.
//
// Les quatre éléments viennent de `architecture.md` § 4.2 et § 4.3 : `numero`,
// `date_document`, le nom du client (`client.nom`, pas `client_id` : le nom est
// ce qui est signé, un identifiant n'est rien pour un tiers), les lignes, et
// le total — qui est une somme, jamais une saisie (ADR-8).

export const LigneCanonique = z.object({
  rang_ligne: z.number().int().min(1),
  designation: z.string().min(1),
  quantite_centimes: z.number().int().nonnegative(),   // 3 -> 300
  montant_centimes: z.number().int().nonnegative(),     // jamais un flottant
});
export type LigneCanonique = z.infer<typeof LigneCanonique>;

export const DevisSignable = z.object({
  numero: z.string().regex(/^D-[0-9]{4}-[0-9]{3,}$/),
  date_document: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  client: z.object({ nom: z.string().min(1) }),
  lignes: z.array(LigneCanonique).min(1),   // B1 : au moins une ligne
  total_centimes: z.number().int().nonnegative(),
});
export type DevisSignable = z.infer<typeof DevisSignable>;
```

**`quantite` et non `prix_unitaire_centimes`.** Le texte canonique porte `quantite
centimes` et `montant centimes`, parce que ce sont les deux nombres qu'un client
compare. Il ne porte pas le prix unitaire, qui n'est qu'un facteur : le changer sans
changer le montant ne change pas le prix affiché, donc ne change pas ce que le client a
accepté.

### 2.2 Types et interfaces

```typescript
// packages/empreinte/src/index.ts

// Le texte canonique. L'ordre des champs est écrit ici et ne bouge jamais ;
// les montants sont des centimes entiers ; aucun formatage local n'intervient.
export function texteCanonique(d: DevisSignable): string;

// SHA-256 des octets UTF-8 du texte canonique, en hexadécimal minuscule.
// Web Crypto est asynchrone : la fonction l'est, et il n'existe pas de
// version synchrone "rapide" qui utiliserait autre chose.
export function empreinte(texte: string): Promise<string>;

// Les 64 caractères, vérifiés. Une empreinte qui ne ressemble pas à une
// empreinte n'est pas une empreinte : c'est une chaîne que rien n'a produite.
export const Empreinte = z.string().regex(/^[0-9a-f]{64}$/);
```

### 2.3 Contrats API

Aucun : F5 ne parle à personne et personne ne l'appelle en réseau. Il est importé par
l'appareil (signer) et par le serveur (recevoir) ; c'est une importation, pas un appel.

Le contrat d'API qui le consomme est écrit dans le plan de `F6` :
`POST /api/v1/devis/:numero/envoi` reçoit `signature.empreinte` **et**
`signature.texte_canonique`, et répond `422` si les deux ne concordent pas.

## 3. Algorithmes critiques

### `texteCanonique` (couvre B3, B10, ADR-6)

La forme est **écrite**, pas déduite :

```
texteCanonique(d):
  parts = []
  parts += "numero="   + d.numero
  parts += "date="     + d.date_document
  parts += "client="   + NFC(d.client.nom)
  parts += "lignes="   + d.lignes.length.toString()
  parts += "total="    + d.total_centimes.toString()      # entier, jamais formaté

  # les lignes suivent, dans l'ordre de rang_ligne
  for l in d.lignes triées par rang_ligne croissant :
    parts += "\nligne=" + l.rang_ligne.toString()
           + "|"       + NFC(l.designation)
           + "|"       + l.quantite_centimes.toString()
           + "|"       + l.montant_centimes.toString()

  return parts.join("|")    # entre l'entête et la 1re ligne, un seul séparateur
```

**La forme exacte, parce qu'une empreinte dépend de la forme :**

```
numero=D-2026-014|date=2026-03-28|client=Roux|lignes=2|total=1440000
```

et, les deux lignes de `architecture.md` § 4.14 ajoutées :

```
…|total=1440000|ligne=1|Pose de trois fenêtres coulissantes|300|1440000|ligne=2|Déplacement offert|100|0
```

Quatre règles dans cette forme, chacune avec sa raison :

| Règle | Raison |
|---|---|
| `\|` entre champs, `\n` avant `ligne=` | Un séparateur unique entre champs, un unique avant la liste des lignes : un champ ne peut donc pas contenir le séparateur sans qu'on le voie. |
| Les lignes sont **triées par `rang_ligne`** | Un serveur qui recevrait les lignes dans un autre ordre doit produire le même octet. Le tri rend l'ordre d'arrivée indifférent. |
| `NFC` sur `nom` et `designation` | `é` précomposé et `e` + U+0301 sont le même mot à l'œil et deux octets différents. Sans NFC, deux appareils produisent deux empreintes du même devis. |
| **Aucun formatage local** | `1 440 000` et `1440000` sont le même montant et deux octets. Aucun `toLocaleString`, aucune `Intl`, aucun séparateur décimal dans le texte canonique. |

### `empreinte` (couvre B10)

```
empreinte(texte):
  octets = UTF-8 encode(texte)          # pas UTF-16, pas la longueur de chaîne
  digest = SHA-256(octets) via crypto.subtle
  return digest en hexadécimal MINUSCULE  # 64 caractères, jamais majuscule
```

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `empreinte_courante` d'un devis | document | `devis.empreinte_courante` (`architecture.md` § 4.2) | à chaque écriture du devis | recalculée à chaque écriture |
| `signature_devis.empreinte` | document, **immuable** | `signature_devis` | à la signature, et **jamais** ensuite | déclencheur `signature_preuve_gele` |
| `facture.empreinte` | document, V1 | `facture` | à l'émission | jamais (gelé) |

**L'empreinte est recalculée à l'écriture, jamais à la lecture.** Une empreinte lue à
la volée serait l'empreinte de ce que la base a sous les yeux, pas de ce qui a été
signé : c'est précisément la différence que `signature_empreinte_verifie` exploite.

## 7. Pièges à éviter

- **Recalculer l'empreinte côté serveur** — ⚠️ Ne pas écrire un SHA-256 dans la route
  serveur ni dans le SQL. Le comportement correct (`30-empreinte.md` § Motifs interdits,
  ADR-6) est **importer** `packages/empreinte` des deux côtés. Deux implémentations
  produisent deux octets, et c'est le risque numéro un du projet (R-01).

- **Mettre un montant en flottant ou formaté dans le texte canonique** — ⚠️ Ne pas écrire
  `(1440000).toLocaleString('fr-FR')`. Le comportement correct est `1440000` en entier,
  et `0.1 + 0.2` n'est pas `0.3` en IEEE 754 : une empreinte qui dépend d'un flottant
  n'est pas une empreinte.

- **Oublier la normalisation NFC** — ⚠️ Ne pas sérialiser `designation` telle quelle. Le
  comportement correct est `designation.normalize('NFC')` sur le nom **et** sur chaque
  désignation, sinon le même devis écrit sur deux appareils a deux empreintes.

- **Trier les lignes à la réception plutôt qu'à la sérialisation** — ⚠️ Ne pas laisser
  l'ordre d'arrivée du tableau décider. Le comportement correct est le tri par
  `rang_ligne` **dans** `texteCanonique`, ce qui rend l'ordre du réseau indifférent.

- **Écrire la date et l'heure de signature dans le texte canonique** — ⚠️ Ne pas ajouter
  `date_signee=…|heure_signee=…`. Le comportement correct est que le texte canonique
  décrit **le devis**, pas **le moment** : sinon resigner le même devis à deux instants
  différents donnerait deux empreintes, et l'archive perdrait le lien entre ce qui a été
  signé et ce qui a été signé plus tard (R-04).
