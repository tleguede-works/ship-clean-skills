## 1. Résumé de la slice

S11 retrouve un dossier client par son nom en deux minutes, **devant un client qui attend au
téléphone**, et demande lequel quand deux clients portent le même nom. C'est le module de
rang 3, et c'est un **appel**, pas une consultation : un client au téléphone qui attend
n'attend pas qu'on cherche dans un menu `Plus`.

Les résultats apparaissent **sous le champ**, pas dans un écran différent : passer à un
autre écran ferait perdre ce qui est tapé si l'appel entrant coupe (E2). Et quand la
recherche ne trouve rien, l'application propose `Nouveau dossier pour M. Roux ?` — parce que
la recherche échoue rarement, et c'est la **création** qui est le plus souvent la bonne
réponse.

**Vague 5** (`index.impl_waves[5]`). Dépend de `F1`, `F2`, `F3`, `F8`, `S1`. Peut être
parallélisée avec `S5`.

  adresse: z.string().min(1),

### 2.2 Types et interfaces

```typescript
// apps/web/app/clients/types.ts

// Les cinq valeurs de `EtatRecherche` du design-system.md § 2.
export type EtatRechercheUI = 'inactif' | 'actif' | 'sans-resultat' | 'plusieurs' | 'erreur';

export type ResultatRecherche = {
  client: Client;
  // L'ADRESSE COMPLÈTE est jointe à chaque résultat. C'est elle qui permet
  // de distinguer deux Roux — pas un numéro interne, pas un_initial.
  nbDevis: number;
};

export type VueRecherche = {
  saisie: string;
  etat: EtatRechercheUI;
  resultats: ResultatRecherche[];
  // L'état `sans-resultat` porte cette proposition. Le nom est celui tapé,
  // pas « le client » : « Nouveau dossier pour M. Roux ? » se lit à voix haute.
  propositionCreation: { nom: string } | null;
  // Les trois noms les plus proches, pour l'état `introuvable` de S12.
  plusProches: string[];
};
```

### 2.3 Contrats API

Aucun : la recherche est **locale**. Un client appelle, Jean-Luc est peut-être dans une cave,
et une recherche qui attend un réseau n'est pas une recherche.

## 3. Algorithmes critiques

### `chercher` (couvre B21, E14)

```
chercher(saisie, base):
  # B21 : trouvables PAR LE NOM DU CLIENT. C'est tout ce que Jean-Luc sait
  # par cœur : il connaît « Roux », il ne connaît pas un identifiant.
  q = saisie.trim().toLowerCase()
  si q == '' → 'inactif'

  # 1. CORRESPONDANCE EXACTE D'ABORD. Un dossier qui s'appelle « Roux » doit
  #    être trouvé quand on tape « Roux ».
  exacts = SELECT * FROM client WHERE lower(nom) = q

  # 2. SI PLUSIEURS EXACTS → 'plusieurs'. E14 : l'application DEMANDE LEQUEL,
  #    elle ne choisit pas. Confondre deux dossiers, c'est envoyer un devis
  #    au mauvais client.
  si |exacts| >= 2 → 'plusieurs', resultats = exacts avec leur adresse complète

  # 3. SINON, PRÉFIXE. C'est ce qui fait que taper « Rou » trouve « Roux ».
  prefixes = SELECT * FROM client WHERE lower(nom) LIKE q || '%'
             ORDER BY length(nom), nom

  si |prefixes| == 1 → 'actif',   resultats = prefixes
  si |prefixes| >  1 → 'plusieurs', resultats = prefixes   # AUCUN présélectionné
  si |prefixes| == 0 → 'sans-resultat',
                        propositionCreation = { nom: saisie.trim() }
                        # « La recherche échoue rarement, c'est la CRÉATION qui
                        #  est le plus souvent la bonne réponse. »
```

### `interruption` (couvre E2 — la raison pour laquelle les résultats sont sous le champ)

```
# E2 : « Le réseau tombe au milieu de la saisie » et, par le même mécanisme,
# l'appel entrant coupe. Les résultats sont donc rendus DANS le même écran,
# sous le champ : changer d'écran ferait perdre ce qui est tapé.
#
# Il n'y a donc pas de `router.push` sur la recherche. La liste de résultats
# est un slot du même écran, et le dossier ne s'ouvre qu'au CHOIX explicite
# d'un client — un geste, pas un effet de frappe.
#
# `popstate` et le bouton `Retour` font la même chose, et aucun des deux ne
# vide la saisie.
```

### `creerDepuisProposition` (couvre B21, E12)

```
creerDepuisProposition(nom):
  # La proposition porte l'adresse et le courriel VIDES, donc le champ
  # adresse est visible et vide dès la création. E12 : l'adresse est celle du
  # dossier, et elle se modifie ICI, une seule fois.
  #
  # Créer un dossier ne crée PAS de devis. `S4` le fera.
  F3.dansTransaction(tx ⇒ INSERT client (nom, adresse = '', courriel = ''))
```

### 4.3 États par écran

Les cinq états sont ceux de l'union **`EtatRecherche`** du `design-system.md` § 2, qui est
la source écrite de cette tranche — pas un fichier `clients.md`, qui n'existe pas.

| État `EtatRecherche` | Condition | Composants affichés | Données |
|---|---|---|---|
| `inactif` | ouverture de l'écran | champ vide, étiquette `Nom du client`, indication `Un seul nom suffit.` | — |
| `actif` | un ou plusieurs caractères saisis, un seul résultat | les résultats **apparaissent sous le champ**, pas dans un écran différent | `ResultatRecherche[]` (1) |
| `sans-resultat` | aucun nom ne correspond | `Aucun client ne porte ce nom.` Puis `Nouveau dossier pour M. Roux ?` en `Bouton` `contour` — la **création** proposée comme la réponse la plus fréquente | `propositionCreation` |
| `plusieurs` | plusieurs correspondances (E14) | les résultats listés avec l'**adresse complète** de chacun. **Aucun n'est présélectionné** | `ResultatRecherche[]` (n) |
| `erreur` | la recherche locale échoue | `La recherche ne respond pas. Vos devis sont encore là.` — parce qu'ils sont dans le magasin local, et le dire évite que Jean-Luc believe les a perdus | — |

**Il n'y a pas d'état `chargement`.** La recherche est un `SELECT` sur SQLite local : elle
répond en moins d'une frame, et un indicateur de chargement serait un mensonge sur la
vitesse (C1).

## 7. Pièges à éviter

- **Naviguer vers un écran de résultats** — ⚠️ Ne pas faire de `router.push` au premier
  caractère. Le comportement correct (E2) est que les résultats sont **sous le champ** dans
  le même écran : changer d'écran ferait perdre ce qui est tapé si l'appel entrant coupe.

- **Présélectionner un résultat** — ⚠️ Ne pas, jamais, dans aucun cas. Le comportement
  correct (E14) est que l'application **demande lequel** : confondre deux dossiers, c'est
  envoyer un devis au mauvais client.

- **Afficher un identifiant interne pour distinguer deux clients** — ⚠️ Ne pas. Le
  comportement correct est l'**adresse complète** de chacun : c'est elle que Jean-Luc peut
  lire au téléphone et reconnaître.

- **Écrire « aucun résultat » quand la recherche échoue** — ⚠️ Ne pas confondre
  `sans-resultat` et `erreur`. Le comportement correct est `La recherche ne respond pas.
  Vos devis sont encore là.` : la base locale est peut-être momentanément inaccessible, et
  dire « aucun client » ferait croire que les dossiers ont disparu.

- **Ajouter un état `chargement`** — ⚠️ Ne pas. Le comportement correct (C1) est qu'il n'y
  en a pas : la recherche est locale et répond en moins d'une frame.

- **Proposer la création à l'état `erreur`** — ⚠️ Ne pas. Le comportement correct est que la
  proposition de création n'existe qu'à l'état `sans-resultat` : quand la recherche **échoue**,
  créer un dossier serait une seconde perte.

- **Mettre `Clients` dans un menu `Plus`** — ⚠️ Ne pas. Le comportement correct
  (`design-system.md` § 3.2) est le rang **3** de la barre basse : on y va quand un client
  appelle, et un client au téléphone qui attend n'attend pas qu'on cherche dans un menu.
