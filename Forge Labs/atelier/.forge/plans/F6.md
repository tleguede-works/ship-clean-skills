## 1. Résumé de la slice

F6 est **le seul point de contact réseau de l'appareil**, et il couvre les deux bouts :
la requête qui part de l'appareil et la route du serveur qui l'exécute. Il envoie par
courriel et **attend le retour du service** avant d'écrire quoi que ce sorte qui dise
« envoyé » (B6).

Il ne fait **jamais** de boucle et **jamais** de délai actif : le client interroge, il ne
retente pas. C'est aussi la raison pour laquelle `architecture.md` § 1.1 refuse une
bibliothèque de client HTTP : une bibliothèque qui réessaie automatiquement violerait
B7 par construction, et B7 est une règle qu'on ne peut pas détecter à la relecture.

**Vague 1** (`index.impl_waves[1]`) — descendue en vague 1 par le plan d'ordonnancement,
avec sa raison dans le front matter de l'architecture : « une transaction locale, un
protocole d'envoi et un rendu de document ne se portent pas par la même personne ».

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// packages/modele/src/confirmation.ts
import { z } from 'zod';

// Les DEUX réponses possibles à un envoi. Il n'y en a pas une troisième :
// « envoyé » n'est pas un troisième état, c'est `confirme` avec son horodatage.
export const Confirmation = z.discriminatedUnion('etat', [
  z.object({
    etat: z.literal('confirme'),
    recu_le: z.string().datetime(),
    adresse: z.string().email(),
  }),
  z.object({
    etat: z.literal('refuse'),
    motif: z.string().min(1),      // « ce que le service a dit », jamais « a échoué »
    reessayable: z.boolean(),
  }),
]);
export type Confirmation = z.infer<typeof Confirmation>;

// L'accusé de réception de la demande, qui n'est PAS une confirmation.
export const EnAttente = z.object({
  etat: z.literal('en_attente'),
  jeton: z.string().min(8),
  demande_le: z.string().datetime(),
});
export type EnAttente = z.infer<typeof EnAttente>;
```

### 2.2 Types et interfaces

```typescript
// apps/web/sorties/courriel.ts

export type EnvoiCourriel = {
  envoyer(d: DevisSignable, jeton: string): Promise<Confirmation | EnAttente>;
  // Une LECTURE. Elle ne peut rien déclencher : c'est ce qui permet de savoir
  // ce qu'il est devenu d'une tentative sans jamais créer de doublon.
  interroger(jeton: string): Promise<Confirmation | EnAttente | 'inconnu'>;
};

export type ErreurReseau =
  | { cas: 'hors-ligne' }        // le réseau manque : rien n'a été tenté
  | { cas: 'timeout' }            // la requête est partie, le retour n'est pas arrivé
  | { cas: 'http'; code: number; message: string }  // ce que le service a dit
  | { cas: 'illisible' };         // réponse illisible : à ne jamais retreated en silence
```

**Les deux délais, et ils ne se confondent pas.** Le délai d'attente réseau est une
constante d'infrastructure (le serveur peut répondre dans le temps). Le délai de relance
d'une facture est une **décision de menuisier** qui n'existe pas (`prd.md` § 12). Le
premier est écrit ici ; le second est absent, et `jourRelance` de `F2` n'est appelé par
personne.

### 2.3 Contrats API

Les cinq endpoints MVP de `architecture.md` § 5. Les deux endpoints V1
(`POST /api/v1/factures`, `POST /api/v1/factures/:numero/relance`) ne sont **pas**
implémentés par cette fondation : ils appartiennent à `S18` et `S20`, qui ne sont pas
planifiables.

```typescript
// apps/web/sorties/client-http.ts — le wrapper de 40 lignes de § 1.1.
// Zéro `setTimeout` d'attente active, zéro boucle, zéro réessai automatique.

export type Reponse =
  | { cas: 'json'; corps: unknown }
  | { cas: 'texte'; corps: string };

export async function appeler(opts: {
  methode: 'GET' | 'POST';
  chemin: string;                    // jamais une URL absolue construite à la main
  jetonAppareil: string | null;      // absent sur POST /api/v1/appareils
  jetonTentative?: string;           // en-tête `jeton-tentative`, § 5
  corps?: unknown;
}): Promise<Reponse | ErreurReseau>;
```

| Route | Méthode | Auth | Ce qu'elle fait |
|---|---|---|---|
| `/api/v1/appareils` | POST | `jeton-une-seule-fois` | échange le lien reçu par courriel contre un jeton d'appareil (§ 5.1) |
| `/api/v1/numeros/reconcilier` | POST | bearer | arbitre un numéro en collision **avant** toute entrée en file (§ 5.2) |
| `/api/v1/archive` | GET | bearer | rend tout ce qui a quitté l'appareil, avec `curseur` (§ 5.3) |
| `/api/v1/devis/:numero/envoi` | POST | bearer + `jeton-tentative` | archive et envoie, idempotent sur `(numero, empreinte)` (§ 5.4) |
| `/api/v1/envois/:jeton` | GET | bearer | **demande au serveur ce qu'il est devenu** d'un jeton (§ 5.5) |

**Placement : les trois premières routes sont portées ici, et c'est une décision.**
`architecture.md` § 3.1 n'attribue **aucune tranche à E11** (changement d'appareil), et
`roadmap.md` § 2.1 ne le compte pas dans le MVP. Ces trois routes ont donc, telles
qu'écrites, **aucune maison** : F6 est le seul nœud dont le périmètre est « les deux
bouts de la frontière appareil ↔ serveur » (§ 2.6), donc elles y vont, avec le réseau
comme seule dépendance commune. Le rapport de cette phase le signale.

## 3. Algorithmes critiques

### `envoyer` (couvre B6, B7, E3, E4, ADR-4)

```
envoyer(d, jeton):
  # 1. LE JETON EST TIRÉ AVANT LE DÉPART. Il est passé en argument, donc
  #    l'appelant l'a déjà tiré et persisté. Rien n'est tiré ici.
  # 2. UN SEUL ESSAI PAR APPEL. Pas de boucle, pas de délai actif.

  r = await appeler({ POST, '/api/v1/devis/' + d.numero + '/envoi',
                      jetonAppareil, jetonTentative: jeton, corps: charge(d) })

  si r est une ErreurReseau :
     # E3 : on ne sait pas si le service a reçu la demande. Le devis reste
     # à `écrit ici, pas encore envoyé`, sa preuve devient `1c`, et
     # l'ENTRÉE DE FILE EST CONSERVÉE. Jamais de second essai automatique.
     retourner { cas: 'sans_reponse', jeton }

  si r.code == 403 : refus — le devis n'est pas signé. Ne rien réessayer.
  si r.code == 422 : refus — empreinte et texte ne concordent pas.
                   # R-01 : la base a recalculé et refusé. C'est un BUG,
                   # pas une erreur de réseau, et il ne doit pas être rejoué.
  si r.code == 200 et corps.etat == 'confirme' :
     retourner corps            # B6 : c'est le SEUL retour qui autorise « envoyé »
  si r.code == 200 et corps.etat == 'en_attente' :
     retourner corps            # la requête est arrivée, le service n'a pas confirmé
  si r.code == 500 :
     # Le § 5.4 : le serveur a PUISSÉ insérer la ligne envoi_courriel. Le rejeu
     # du même jeton la retrouve. Donc l'appareil doit REJOUER LE MÊME JETON,
     # jamais en tirer un nouveau.
     retourner { cas: 'rejetable', jeton }
```

### `interroger` (couvre E3, ADR-4)

```
interroger(jeton):
  r = await appeler({ GET, '/api/v1/envois/' + jeton, jetonAppareil })
  si r.code == 404 → 'inconnu'
     # § 5.5 : un 404 ici est une RÉPONSE, pas une erreur. Le serveur n'a jamais
     # reçu cette tentative, donc aucun courriel n'est parti, donc Jean-Luc peut
     # réessayer AVEC LE MÊME JETON, sans risque de doublon.
  si r.code == 200 → corps
  si ErreurReseau → ne rien écrire, laisser l'entrée `en_attente`
```

### La politique de réessai, en une phrase

**Il n'y a pas de politique de réessai.** Ce qui existe, c'est : *le même jeton, et
l'utilisateur qui décide*. Un délai actif serait une attente que Jean-Luc ne peut pas
quitter ; une boucle automatique produirait un second courriel (B7).

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Jeton d'appareil | appareil | magasin local `F3`, jamais affiché | à l'échange du lien reçu | jamais |
| `jeton_tentative` d'un devis | appareil | `devis.jeton_tentative` (colonne d'appareil) | **avant** le départ | jamais |
| `tentative_le` | appareil | `devis.tentative_le`, horloge `F2` | au départ | à chaque départ |
| `confirme_le` / `refuse_par` | serveur | `envoi_courriel` | horloge serveur | une seule fois, jamais retirée (G5) |

**Le jeton d'appareil est le seul secret du produit, et il n'est jamais demandé.**
`architecture.md` § 5 : 32 octets tirés une fois, reçus par courriel, conservés dans le
magasin local, jamais affichés, jamais demandés. C'est la seule identité technique, et
sa faiblesse est écrite : un appareil volé donne le jeton, parce qu'il n'y a pas de
seconde serrure (R-03, B22, C2).

## 7. Pièges à éviter

- **Utiliser une bibliothèque de client HTTP** — ⚠️ Ne pas écrire
  `const api = ky.create({ retry: 3 })`. Le comportement correct (`architecture.md` § 1.1)
  est un wrapper de 40 lignes : une bibliothèque qui réessaie automatiquement violerait
  B7 **par construction**, et ce défaut ne se voit pas à la relecture.

- **Afficher « envoyé » sur un `en_attente`** — ⚠️ Ne pas traiter
  `{ etat: 'en_attente' }` comme un succès HTTP. Le comportement correct (B6) est que le
  devis reste à `écrit ici, pas encore envoyé` et que sa preuve devient `1c`. Le `500` de
  `§ 5.4` ne change rien : le serveur a peut-être déjà inséré la ligne.

- **Tirer un nouveau jeton sur un `500`** — ⚠️ Ne pas faire
  `jeton = nouveauJeton()` dans le `catch`. Le comportement correct (§ 5.4) est de
  **rejouer le même jeton** : c'est lui qui retrouve l'enregistrement éventuellement
  inséré, donc c'est lui qui empêche le doublon.

- **Faire une boucle de `interroger`** — ⚠️ Ne pas écrire `while (!confirme) await
  interroger(jeton)`. Le comportement correct (`20-ecriture-locale.md`) est que **le
  client interroge** : il n'y a aucun délai actif, et Jean-Luc doit pouvoir poser le
  téléphone.

- **Réécrire le devis à la réception** — ⚠️ Ne pas faire de mise à jour partielle sur
  `POST /envoi`. Le comportement correct (ADR-3) est que le serveur **archive** et
  **envoie** : un refus devient un état visible sur le devis, jamais une reprise
  silencieuse.

- **Ajouter une boucle de fusion** — ⚠️ Ne pas implémenter de CRDT ni de « dernière
  écriture gagne ». Le comportement correct (ADR-3) est : il n'y a qu'un écrivain, donc il
  n'y a rien à arbitrer.
