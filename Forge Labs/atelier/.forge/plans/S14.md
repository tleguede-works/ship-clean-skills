## 1. Résumé de la slice

S14 télécharge **tous les devis et toutes les factures dans un seul fichier, à tout moment,
sans rien payer**. C'est l'engagement du contrat § 3 qui rend crédible la promesse de
pouvoir partir : un MVP où Jean-Luc paie 5,99 €/mois et ne peut pas sortir ses documents rend
ce bloc faux.

Le fichier est produit **sur l'appareil**, hors ligne, à partir du magasin local. Le
`design-system.md` § 2 ne dessine `PanneauExport` qu'avec trois états et **aucun** état
d'erreur — parce que la conception dit qu'un export ne peut pas échouer, et c'est vrai
seulement si le rendu est local (ADR-9).

**Vague 8** (`index.impl_waves[8]`). Dépend de `F1`, `F3`, `F7`, `F8`, `S12`. Peut être
parallélisée avec `S9`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/app/reglages/export.ts
import { z } from 'zod';

// C6 : « Les factures sont conservées 10 ans, les devis 2 ans, les
// sauvegardes 30 jours. L'export de tout est possible en permanence,
// sans frais. »
//
// Le fichier est donc TOUJOURS produit, et il contient TOUT. Il n'existe pas
// de filtre par période, pas de « devis de cette année », et pas de
// purge : une période de conservation qui retire des documents d'un export
// ferait de l'export une copie partielle, et B24 promet « tous ».
export const ContenuExport = z.object({
  devis: z.array(DevisExporte).min(0),   // 0 est permis : un export sur une
                                          // installation neuve est valide
  factures: z.array(FactureExportee).min(0),
});
export type ContenuExport = z.infer<typeof ContenuExport>;

export const DevisExporte = z.object({
  numero: z.string().regex(/^D-[0-9]{4}-[0-9]{3,}$/),
  date_document: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  client: z.object({ nom: z.string(), adresse: z.string(), courriel: z.string().email() }),
  lignes: z.array(z.object({
    rang_ligne: z.number().int().min(1),
    designation: z.string(),
    quantite_centimes: z.number().int().nonnegative(),
    prix_unitaire_centimes: z.number().int().nonnegative(),
    montant_centimes: z.number().int().nonnegative(),
  })),
  total_centimes: z.number().int().nonnegative(),
  // L'empreinte SIGNÉE quand il y en a une, et elle est ce qui rend le
  // document opposable hors de l'application. C'est la raison pour laquelle
  // l'export vaut quelque chose : ce n'est pas une copie de l'écran, c'est
  // l'archive de ce qui a été signé (prd.md § 7.2).
  empreinte_signee: z.string().regex(/^[0-9a-f]{64}$/).nullable(),
  texte_canonique: z.string().nullable(),
});
```

### 2.3 Contrats API

Aucun. `GET /api/v1/archive` (§ 5.3) **existe** et remplit le magasin local à chaque
contact avec le réseau : c'est ce qui rend l'export complet même après un changement
d'appareil (E11, ADR-9). Mais l'export lui-même **n'appelle rien** — il lit le magasin
local, comme tout le reste.

## 3. Algorithmes critiques

### `construire` (couvre B24, C6, ADR-9)

```
construire(magasin, sourceF2):
  # 1. TOUT, depuis le magasin local. Aucune requête, aucune période, aucun filtre.
  devis    = SELECT * FROM devis      ORDER BY date_document
  factures = SELECT * FROM facture    ORDER BY date_facture   # vide au MVP

  # 2. Pour chaque devis, le texte canonique ET l'empreinte signée quand il y en a
  #    une. Sans eux, l'export serait une copie d'écran : on ne pourrait pas
  #    vérifier ce qui a été signé. C'est prd.md § 7.2 : « un devis signé est
  #    conservé avec l'empreinte de son texte ».
  #
  # 3. Les octets sortent de F7, qui produit le PDF sur l'appareil.
  #    delegated : F7.rendre(devisSignable, empreinte_signee ?? empreinte_courante)
  #
  # 4. LE NOM DU FICHIER PORTE LA DATE DU JOUR, lue par F2.
  nomFichier = "atelier-devis-" + sourceF2.maintenant().dateFr + ".pdf"
  octets     = … concaténer tous les PDF, dans l'ordre des dates
  taille     = octets.length
  return { nomFichier, taille_octets: taille, octets }
```

**Les factures vides ne produisent pas une page « aucune facture ».** Au MVP il n'y en a
aucune (`roadmap.md` § 2.2), et l'export est complet au sens de B24 : l'ensemble des
factures est vide, donc l'export contient tout ce qui existe. `roadmap.md` § 2.3 le dit
explicitement, et ajoute que la promesse redevient contraignante à la V1.

### `etatsDuPanneau` (couvre ADR-9)

```
etatsDuPanneau():
  'inactif'    → « Vos devis et vos factures, dans un seul fichier. »
                 « Ce téléchargement est permanent et ne coûte rien. »
                 + bouton « Tout télécharger »
                 # AUCUN compte, AUCUN abonnement, AUCUNE « version premium » en dessous.
  'preparation'→ « Préparation en cours. »
                 # PAS DE BARRE DE PROGRESSION : l'export n'est pas un envoi, et
                 # un pourcentage serait un chiffre que le produit n'a pas.
                 # Le bouton est `desactive`, PAS masqué : il reste à la même
                 # place, donc l'écran ne bouge pas.
  'pret'       → « Le fichier est prêt. » + nom + taille + « Enregistrer » + « Partager »

# ET RIEN D'AUTRE. Pas de `echec`, pas de `annule`, pas de `partiel`.
#
# `design-system.md` § 2 dessine ces trois états et AUCUN état d'erreur,
# parce que le rendu est local et n'a pas de phase qui puisse échouer seule.
# ADR-9 : « Un service de rendu distant ferait dépendre US-4 du réseau ».
#
# `dossier-client.md` § 4 et `reglages.md` § 4 citent pourtant un « PanneauExport
# état echec » qui n'existe pas dans l'union. C'est une divergence du design ;
# ce plan applique l'union du § 2, et le rapport de la phase la signale.
```

### `jamaisPayant` (couvre B24, C10, C6)

```
# Une fonction par écran qui rend un `PanneauExport` doit être appelable sans
# qu'aucune condition ne filtre son rendu. La règle est rendue EXÉCUTABLE :
# `PanneauExport` ne reçoit aucune prop du type `peutPayer`, `estPayant`,
# `estPremium`, `requiertAbonnement`.
#
# `grep -rni 'premium\|paiement\|abonnement\|licence' apps/web/app/reglages/` doit
# rendre 0. Un export qui devient payant « juste pour un petit.doc » n'est pas
# une fonction de produit, c'est un manquement au contrat § 3.
```

lui donner une fréquence qu'il n'a pas »).

### 4.3 États par écran

Le panneau a **trois** états, et c'est le `design-system.md` § 2 qui les nomme.

| État `EtatPanneauExport` | Condition | Composants affichés | Données |
|---|---|---|---|
| `inactif` | repos | `Vos devis et vos factures, dans un seul fichier.` puis `Ce téléchargement est permanent et ne coûte rien.` puis `Tout télécharger`. **Aucun compte, aucun abonnement, aucune « version premium » en dessous** | — |
| `preparation` | préparation du fichier | `Préparation en cours.` **Pas de barre de progression** : l'export n'est pas un envoi, et un pourcentage serait un chiffre que le produit n'a pas. Le bouton est `desactive`, **pas masqué** : il reste à la même place, donc l'écran ne bouge pas | — |
| `pret` | le fichier est prêt | `Le fichier est prêt.` puis le nom du fichier et sa taille — `atelier-devis-2026-04-12.pdf`, `2,4 Mo` — puis `Enregistrer` et `Partager` | `ExportPret` |

**Il n'y a pas d'état d'erreur, et c'est une décision vérifiable.** Un état d'erreur
supposerait une phase qui puisse échouer seule : ici, le rendu est local (ADR-9), donc
l'export ne peut échouer que si l'appareil manque de place, ce qui est un fait matériel
qui ne se traduit pas par une faute du produit.

### 4.4 Formulaires

| Formulaire | Bibliothèque | Schéma | Soumission | Gestion d'erreur |
|---|---|---|---|---|
| Export de tout | aucun formulaire | `ContenuExport` (Zod) | `Tout télécharger` → `Enregistrer` ou `Partager` | pas de formulaire d'options : il n'y a **rien à choisir**. Ni période, ni format, ni filtre. Un export avec des options est un export dont la complétude est discutable |

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `etat` du panneau | écran | état local | `inactif` | `preparation` → `pret` |
| `octets` du fichier | écran | variable locale | après `Tout télécharger` | jamais — le fichier est **jetable**, le fait qu'il ait pu être fait ne l'est pas |
| `nomFichier`, `taille` | écran | dérivés des octets | idem | jamais |
| Contenu exporté | appareil | **lu**, jamais écrit : le magasin local est la source | — | — |
| Prix affiché | — | **écrit dans le code** | — | jamais |

**L'export ne crée aucune donnée.** Il ne modifie ni le magasin local, ni le serveur, ni
`configuration`. Un export qui laisse une trace dans le produit est une export qui peut
échouer en écrivant, et alors il aurait un état d'erreur.

## 7. Pièges à éviter

- **Ajouter un état d'erreur à `PanneauExport`** — ⚠️ Ne pas. Le comportement correct
  (ADR-9, `design-system.md` § 2) est que le panneau a **trois** états et qu'aucun n'est
  une erreur, parce que le rendu est local et n'a pas de phase qui puisse échouer seule.
  Les § 4 de `dossier-client.md` et de `reglages.md` en citent un : c'est une divergence du
  design, signalée, et ce plan applique l'union du § 2.

- **Mettre une barre de progression** — ⚠️ Ne pas. Le comportement correct
  (`design-system.md` § 2) est `Préparation en cours.` **sans** barre : l'export n'est pas
  un envoi, et un pourcentage serait un chiffre que le produit n'a pas.

- **Masquer le bouton pendant la préparation** — ⚠️ Ne pas. Le comportement correct est qu'il
  passe `desactive` **à la même place**, pour que l'écran ne bouge pas.

- **Proposer un filtre de période** — ⚠️ Ne pas. Le comportement correct (B24) est que
  l'export contient **tout** : un filtre par période ferait de l'export une copie
  partielle, et C6 dit que les factures sont conservées dix ans.

- **Rendre l'export payant, même « juste pour un petit.doc »** — ⚠️ Ne pas. Le
  comportement correct (C10) est que rien d'autre n'est à payer tant que Jean-Luc reste en
  virement et en signature tracée. `grep -rni 'premium\|paiement\|abonnement\|licence'
  apps/web/app/reglages/` doit rendre **0**.

- **Exporter depuis le serveur** — ⚠️ Ne pas. Le comportement correct (ADR-9) est que le
  fichier est produit **sur l'appareil**, à partir du magasin local : un rendu distant
  serait un acteur supplémentaire, interdit par C11, et ferait dépendre l'export du réseau.

- **Oublier l'empreinte et le texte canonique dans l'export** — ⚠️ Ne pas exporter seulement
  ce qui est affiché. Le comportement correct (`prd.md` § 7.2) est que l'export contient,
  pour chaque devis signé, **l'empreinte de son texte** : sans elle, le fichier est une copie
  d'écran et non une archive opposable.

- **Écrire une trace de l'export** — ⚠️ Ne pas ajouter une ligne « export effectué ». Le
  comportement correct est que l'export **n'écrit rien** : une trace le ferait dépendre d'une
  écriture, donc susceptible d'échouer, donc il aurait un état d'erreur.

## 10. Critères d'acceptation

- [ ] B24 : l'export contient **tous** les devis et **toutes** les factures, sans période ni filtre, et sa signature ne prend aucun paramètre de période.
- [ ] B24 / C10 : `grep -rni 'premium\|paiement\|abonnement\|licence' apps/web/app/reglages/` rend **0**, et `PanneauExport` ne reçoit aucune prop de paiement.
- [ ] C6 : un export sur une installation neuve est **valide** et produit un fichier vide — pas une erreur.
- [ ] ADR-9 : `EtatPanneauExport` ne contient que `inactif`, `preparation`, `pret`, et `grep -rn 'fetch' apps/web/app/reglages/` rend **0`.
- [ ] `design-system.md` § 2 : à l'état `preparation`, il n'y a **ni** barre de progression **ni** pourcentage, et le bouton reste visible en `aria-disabled`.
- [ ] L'export **n'écrit rien** : `devis`, `facture`, `configuration` et `sortie_devis` ont les mêmes comptages avant et après.
- [ ] `prd.md` § 7.2 : chaque devis signé exporté porte l'empreinte de son texte dans les octets produits.
