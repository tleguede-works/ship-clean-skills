## 1. Résumé de la slice

S4 commence un devis en déposant le nom du client, **hors réseau, sans rien demander**.
C'est l'acte que le PRD § 1.1 nomme comme problème principal, et aucun module n'existe
sans lui.

Une chose est easy à dire et difficile à tenir : **à l'état `partiel` de `EnTeteDevis`, aucun
numéro et aucune date ne s'affichent.** Un numéro afficherait une identité qui n'existe pas
encore, et `devis.numero` est une clé primaire non réattribuée : lui en montrer un avant
qu'il soit écrit en ferait une identité qu'il ne faut pas pouvoir changer.

**Vague 4** (`index.impl_waves[4]`). Dépend de `F1`, `F2`, `F3`, `F8`. Peut être
parallélisée avec `S1` et `S13`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// packages/modele/src/client.ts
import { z } from 'zod';

// `nom` n'est PAS unique. E14 : deux clients peuvent porter le même nom, et
// les confondre, c'est envoyer un devis au mauvais client. L'unicité est donc
// une contrainte de l'INTERFACE (S11 demande lequel), jamais de la base.
export const Client = z.object({
  client_id: z.string().uuid(),
  nom: z.string().refine((s) => s.trim().length > 0, {
    message: 'Le nom du client ne peut pas être vide.' }),
  adresse: z.string().min(1),
  courriel: z.string().email(),
});
export type Client = z.infer<typeof Client>;
```

```typescript
// apps/web/app/devis-nouveau/saisie.ts

// B1 énumère LES QUATRE éléments. Le schéma les rend tous requis, et c'est
// la seule façon de faire échouer l'enregistrement **avant** tout INSERT :
// un devis écrit à moitié est un devis que la liste affiche et que rien ne
// peut relire.
export const NouveauDevis = z.object({
  client: Client,
  date_document: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  duree_validite_jours: z.union([z.literal(15), z.literal(30), z.literal(60)]),
  lignes: z.array(LigneCanonique).min(1, {
    message: 'Un devis porte au moins une ligne de travaux.' }),
});
export type NouveauDevis = z.infer<typeof NouveauDevis>;
```

### 2.2 Types et interfaces

```typescript
// apps/web/app/devis-nouveau/types.ts

// Ce que l'écran sait, et rien de plus. `numero` est `null` tant que le devis

```

## 3. Algorithmes critiques

### `numeroSuivant` (couvre B1)

```
numeroSuivant(client_id, sourceF2, appareil):
  # B1 : « L'identifiant est définitif : il n'est ni réattribué ni réutilisé. »
  # Donc il est tiré UNE FOIS, sur l'appareil, et ne bouge plus.
  annee = sourceF2.maintenant().dateFr.take(4)      # ← l'heure de F2, nulle part ailleurs
  dernier = SELECT coalesce(max(séquence), 0) FROM devis WHERE année = annee
  # La réconciliation § 5.2 peut avoir signalé une collision : le numéro est
  # alors remplacé AVANT toute écriture, parce que rien n'a encore quitté l'appareil.
  si numéro en conflit avec le registre du serveur :
      demander un numéro frais à /api/v1/numeros/reconcilier
  return « D-» + annee + «-» + (dernier + 1) en 3 chiffres
```

**Ce numéro est tiré à l'écriture, pas à l'ouverture de l'écran.** Tant que le devis
n'est pas enregistré, `SaisieNouveauDevis.numero` vaut `null` et l'en-tête affiche
`Devis en cours — pas encore enregistré`.

### `validerB1` (couvre B1)

```
validerB1(saisie):
  manquants = []
  si saisie.client == null                    → manquants += 'le nom du client'
  si saisie.date_document == null             → manquants += 'la date'
  si saisie.lignes.length == 0                → manquants += 'une ligne de travaux'
  si manquants non vide :
      renvoyer { refus: 'Il manque : ' + manquants.join(', ') + '.' }
      # La phrase dit ce qu'il faut FAIRE, jamais ce qui est invalide.
  sinon :
      renvoyer { ok: saisie }
```

**Le refus n'est ni une modale ni un toast.** Le bouton de la barre d'action reste visible
et passe à l'état `desactive`, avec la raison écrite **juste au-dessus** de lui : un devis
se remplit debout, une modale à remplir serait une modale à fermer.

### `dureeParDefaut` (couvre B12, C2)

```
dureeParDefaut(appareil):
  # B12 : « 30 jours par défaut ». Le défaut est lu dans `configuration`, et
  # il est 30 tant qu'il n'a jamais été posé : un réglage ABSENT est un
  # réglage jamais posé, ce qui est différent d'un réglage à `faux`.
  v = configuration['duree_validite_jours']
  return v ∈ {15, 30, 60} ? v : 30
```

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `SaisieNouveauDevis` | écran | état local de `useState` | `duree_validite_jours` depuis `configuration`, le reste `null` / `[]` | à chaque frappe |

**Le numéro n'est pas dans l'état local de l'écran.** Il n'existe qu'après
l'enregistrement, parce qu'il est une clé primaire non réattribuée : le montrer dans un
champ éditable rendrait possible un numéro réattribué, ce que B1 interdit.

## 7. Pièges à éviter

- **Afficher un numéro avant l'enregistrement** — ⚠️ Ne pas tirer un numéro à l'ouverture
  du formulaire. Le comportement correct (B1, `devis-nouveau.md` § 4) est `EnTeteDevis`
  à l'état `partiel` : `Devis en cours — pas encore enregistré`, **aucun numéro, aucune
  date**. Un numéro afficherait une identité qui n'existe pas encore.

- **Écrire le devis dans le magasin avant que les quatre éléments soient réunis** — ⚠️
  Ne pas créer une ligne `devis` à la première frappe du nom. Le comportement correct (B1)
  est le refus en amont : `Il manque : une ligne de travaux.` Un devis à moitié écrit
  apparaît dans la liste et ne peut pas être relu.

- **Mettre une modale ou un toast pour le refus** — ⚠️ Ne pas alerter. Le comportement
  correct est le bouton **visible** et `desactive`, avec la raison écrite juste au-dessus.
  Jean-Luc remplit un devis debout, devant un client qui attend : une modale est une chose
  à fermer.

- **Écrire « le champ est invalide »** — ⚠️ Ne pas afficher le nom du champ technique. Le
  comportement correct est l'action : `Écrivez la quantité, ou effacez la ligne.`

- **Faire une recherche réseau pour le nom du client** — ⚠️ Ne pas interroger le serveur.
  Le comportement correct (C1, E2) est que la recherche est **locale** : elle est dans
  SQLite sur OPFS, donc elle répond dans une cave.

- **Créer un dossier client automatiquement sur une correspondance approchée** — ⚠️ Ne pas
  suggérer une correspondance approximative comme si c'était le bon client. Le
  comportement correct (E14) est que `ChampRecherche` à l'état `plusieurs` **liste les
  adresses complètes et n'en présélectionne aucune**.

## 10. Critères d'acceptation

- [ ] B1 : chacun des quatre éléments manquants produit le message exact correspondant, et **rien n'est écrit** dans `F3` dans les trois cas d'échec.
- [ ] B1 : à l'état `partiel`, le DOM ne contient aucun numéro de devis.
- [ ] B1 / E14 : deux devis du même client le même jour ont deux numéros distincts, et la séquence ne recule jamais.
- [ ] B12 : le défaut de durée vaut 30 quand `configuration` est vide, et un changement de défaut ne s'applique pas à un devis déjà écrit.
- [ ] US-1 : un devis enregistré puis relu est identique `numero`, `client.nom`, `date_document`.
- [ ] C1 : `npx vitest run devis-nouveau` passe avec un compteur `fetch` à 0.
- [ ] E14 : deux dossiers de même nom sont listés avec leurs adresses et **aucun** n'est présélectionné.
