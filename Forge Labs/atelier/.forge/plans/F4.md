## 1. Résumé de la slice

F4 décide **dans quel ordre** ce qui est parti vers le service de courriel, et **ce qui rend
une entrée invalide**. L'ordre est le **rang monotone** attribué par `F3` à l'écriture,
et rien d'autre. Ce n'est pas une préférence : c'est la seule ordre qui soit reproductible
quand l'horloge du téléphone se trompe, et la seule que Jean-Luc puisse redire au téléphone
(« celui-là d'abord »).

L'invalidation se produit **à l'écriture du devis**, jamais au moment de l'envoi
(ADR-2) : une écriture de devis compare `devis.empreinte_courante` à
`signature_devis.empreinte`, et dès qu'elles diffèrent l'entrée est invalidée avec la
raison `signature annulée par une modification (B11)` — et **elle reste visible**.

`FileAttente`, le composant de `design-system.md` § 2, est la face visible de cette
fondation ; cette fondation est le mécanisme.

**Vague 2** (`index.impl_waves[2]`). Dépend de `F2`, `F3`, `F5`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/file/schemas.ts
import { z } from 'zod';

// Le jeton est tiré AVANT le départ et rejoué au besoin (E3, E4, ADR-4).
// Il est donc présent dès l'entrée dans la file, jamais après.
export const JetonTentative = z.string().min(8);

// `rang` est fourni par F3 et n'est jamais calculé ici. Un `rang` nul est
// refusé : une entrée sans rang n'a pas de place dans l'ordre.
export const EntreeFile = z.object({
  jeton: JetonTentative,
  numero: z.string().regex(/^D-[0-9]{4}-[0-9]{3,}$/),
  empreinte: z.string().regex(/^[0-9a-f]{64}$/),
  rang: z.number().int().positive(),
  etat: z.enum(['en_attente', 'confirme', 'echoue', 'invalide']),
  tente_le: z.string().datetime().nullable(),   // horloge F2 — jamais la clé de tri
  erreur: z.string().nullable(),               // ce que le service a dit
  raison_invalidation: z.string().nullable(),   // ADR-2 : jamais supprimée
});
export type EntreeFile = z.infer<typeof EntreeFile>;
```

**`etat` a quatre valeurs, et `invalide` est la quatrième.** Les trois de
`EtatSortie` (`architecture.md` § 2.1) sont des états **affichés** ; `invalide` est un
état **d'entrée de file** qui n'a pas de pendant dans le vocabulaire du document : un
devis invalidé est `attente` ou `confirme` du point de vue de son état de sortie, et il
est en même temps retiré du départ. Confondre les deux vocabulaires est exactement le
mélange que la § 4.6 de `design-system.md` refuse.

### 2.2 Types et interfaces

```typescript
// apps/web/file/file-attente.ts

// Une entrée entre dans la file par cette fonction, et par aucune autre.
export function entrer(f: FileAttente, e: {
  jeton: string; numero: string; empreinte: string; rang: number;
}): void;

// Le tri n'est pas un paramètre : il est écrit ici, une fois.
// C'est le SEUL endroit du produit où l'ordre de sortie est décidé.
export function* dansLordre(): AsyncGenerator<EntreeFile>;

// L'invalidation se produit à l'écriture du devis, jamais à l'envoi.
export function invalider(f: FileAttente, numero: string, raison: string): void;

export type FileAttente = {
  entrees: EntreeFile[];         // l'ordre du tableau n'est PAS l'ordre de sortie
  parNumero: Map<string, EntreeFile>;
};
```

### 2.3 Contrats API

Aucun : F4 ne parle à personne. Il **commande** `F6` (qui parle au service) et il **lit**
`F3` (qui fournit le rang). La relation est un appel direct de fonction, donc elle est
instrumentable par un faux `EnvoiCourriel` sans réseau ni serveur.

## 3. Algorithmes critiques

### `dansLordre` (couvre ADR-1, R-06)

**C'est l'algorithme le plus important de cette fondation, et il tient en une ligne.**

```
dansLordre():
  # LA LIGNE QUI DOIT ÊTRE ÉCRITE COMME ÇA :
  #   tri par rang croissant, et par rien d'autre.
  #   ni par tente_le, ni par la date du document, ni par le jeton,
  #   ni par l'état, ni par l'ordre d'insertion.
 Snapshot ← copie des entrées dont etat = 'en_attente'
           OU etat = 'invalide'      # une entrée invalidée reste visible
  trier Snapshot par rang croissant, puis par numero croissant (tie-break
  déterministe : deux devis ne peuvent pas partager un rang, donc le
  tie-break ne sert qu'à ce que le test soit reproductible)
  pour chaque entrée dans Snapshot : la rendre

# Ce qui est ABSENT, et son absence est le contrat :
#   * aucun appel à maintenant() / sourceSysteme()  → l'ordre ne dépend d'aucune heure
#   * aucun tri par tente_le                        → l'heure d'un chantier est fausse
#   * aucun tri par date_document                   → B12 : elle ne fait pas foi
#   * aucune suppression d'entrée                   → ADR-2
```

### `entrer` (couvre ADR-4, E3, E4)

```
entrer(f, e):
  # E4 : un devis n'est envoyé qu'une fois par action. Un second appui avec
  # le MÊME jeton ne crée pas de seconde entrée et ne ré-envoie rien.
  si f.parNumero.existe(e.numero) et même jeton → ne rien faire, retourner
  # B7 : la clef d'idempotence est (numero, empreinte), pas le jeton. Un devis
  # resigné a une empreinte différente et DOIT pouvoir repartir.
  si f.parNumero.existe(e.numero) et empreinte différente →
     créer une NOUVELLE entrée avec le nouveau rang fourni par F3
  sinon →
     entrée = { jeton, numero, empreinte, rang, etat: 'en_attente',
                tente_le: horlogeSysteme().maintenant().epochMs → iso,
                erreur: null, raison_invalidation: null }
     ajouter à f.entrees et à f.parNumero
```

### `invalider` (couvre ADR-2, B11, E6)

```
invalider(f, numero, raison):
  e = f.parNumero.get(numero)
  si e n'existe pas → ne rien faire
  si e.etat == 'confirme' → ne rien faire et le dire
      # G5 : une confirmation reçue ne se retire pas. B6 est la règle centrale.
  e.etat = 'invalide'
  e.raison_invalidation = raison        # ex. "signature annulée par une modification (B11)"
  # e reste dans f.entrees : une entrée qui disparaît de la liste est un devis
  # que Jean-Luc croit parti.

appliquer(f, devis):                       # appelé par F3, dans la transaction
  si devis.empreinte_courante != devis.empreinte_signee →
     invalider(f, devis.numero, "signature annulée par une modification (B11)")
```

**Le nom de la fonction est le nom de l'opération interdite** (`architecture.md` § 2.4) :
`invalider` est l'opération que rien n'a le droit de contourner, donc elle porte ce mot.

### Le test qui prouve le tri — **nom exact**

Fichier : `apps/web/file/file-attente.test.ts`

```
describe('FileAttente / ordre de sortie')
```

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `EntreeFile[]` | appareil | SQLite sur OPFS, table `devis` (`rang_entree`, `jeton_tentative`, `tentative_le`, `sync_etat`) | à la première entrée en file | par `entrer`, `invalider`, et la confirmation de `F6` |
| Rang d'entrée | appareil | `F3` (`rang_suivant`) | à l'écriture | jamais par la file |
| Bandeau et compteur | globale | magasin Zustand de `F8` | au démarrage | par `F4`, jamais par un écran |

**La file ne possède pas de copie persistante à elle.** Une entrée de file est un **état
de la ligne `devis`** : `rang_entree`, `jeton_tentative`, `tentative_le`, `sync_etat`.
Une table `file` séparée serait une deuxième vérité sur l'état d'un devis, et c'est
exactement ce qu'ADR-3 interdit (« un seul écrivain, donc il n'y a rien à arbitrer »).

## 6. Traçabilité des règles

### 6.1 Règles métier (B*)

| ID | Règle (PRD) | Implémentée où | Approche |
|---|---|---|---|
| B4 | Une écriture passe par l'appareil avant toute action vers l'extérieur | `entrer` refuse une entrée sans `rang` fourni par `F3` | pas d'entrée sans rang, donc pas d'envoi avant que le devis soit écrit |
| B5 | Trois états de sortie, changés sur action explicite | § 3 `dansLordre` ne trie pas par état et ne modifie aucun état de sortie | la file ne décide pas si un devis est sorti |
| B6 | `envoyé par courriel` ne s'affiche qu'après confirmation | `invalider` refuse de toucher une entrée `confirme` | une confirmation ne se retire pas (G5) |
| B7 | Un devis n'est envoyé qu'une fois par action | § 3 `entrer`, clef `(numero, empreinte)` + jeton | ADR-4 ; la garde `G4` tient la porte côté serveur |
| B11 | Modifier après signature annule la signature | § 3 `appliquer` compare `empreinte_courante` et `empreinte_signee` | invalidation à l'écriture, pas à l'envoi (ADR-2) |
| B23 | Le compteur de devis non envoyés est exact | `dansLordre` rend les `en_attente` ; `F8` les compte | le compteur baisse au moment exact de la confirmation |

| E3 | Le réseau tombe après l'envoi, avant la confirmation | l'entrée reste `en_attente`, `tente_le` est écrit, l'état de sortie du devis reste `attente` avec la preuve `1c` | `idempotence.test.ts` |

## 7. Pièges à éviter

- **Trier la file par `tente_le`** — ⚠️ Ne pas écrire
  `[...entrees].sort((a, b) => a.tente_le.localeCompare(b.tente_le))`. Le comportement
  correct (ADR-1, `20-ecriture-locale.md` § Motifs interdits) est le tri par `rang`, et il
  est écrit **une fois**, dans `dansLordre`. L'ordre obtenu par `tente_le` est plausible,
  reproductible sur un bureau, et faux sur un terrain.

- **Passer le tri en paramètre de `dansLordre`** — ⚠️ Ne pas écrire
  `dansLordre('rang' | 'tente_le')`. Le comportement correct est qu'il n'existe
  qu'un seul ordre, donc la fonction ne prend aucun paramètre : un choix possible est un
  choix qui sera fait un jour par erreur.

- **Supprimer l'entrée invalidée** — ⚠️ Ne pas faire
  `f.entrees = f.entrees.filter(e => e.numero !== numero)` dans `invalider`. Le
  comportement correct (ADR-2) est de **garder** l'entrée avec `etat: 'invalide'` et sa
  raison : une entrée qui disparaît est un devis que Jean-Luc croit parti.

- **Faire boucler l'envoi tout seul** — ⚠️ Ne pas écrire de `setTimeout` d'attente active
  ni de boucle de réessai dans la sortie de file. Le comportement correct
  (`20-ecriture-locale.md`) est que **le client interroge** : il ne boucle pas, il n'y a
  aucun délai actif, et le jeton de tentative est tiré avant le départ.

- **Afficher un pourcentage dans le bandeau** — ⚠️ Ne pas ajouter une barre de progression
  à l'état `attente`. Le comportement correct (R-06, `design-system.md` § 2) est un
  nombre et une promesse : `N devis attendent la confirmation` et `repartiraient seuls`.

- **Réutiliser une empreinte pour faire partir un envoi qui échouerait** — ⚠️ Ne pas
 n'ont pas `empreinte_courante` là où l'empreinte **signée** est attendue. Le
  comportement correct (`30-empreinte.md` § Priorité) est que l'entrée de file porte
  l'empreinte **signée**, au moment de la signature.

## 10. Critères d'acceptation

- [ ] ADR-1 : `npx vitest run file-attente` rend `pass` sur

- [ ] ADR-1 : **la même commande échoue** quand `dansLordre` est muté pour trier par `tente_le`. C'est cette seconde ligne, et non la première, qui prouve que le test mord.
