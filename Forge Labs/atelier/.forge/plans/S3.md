## 1. Résumé de la slice

S3 dit qu'un devis est arrivé au terme de sa validité, et demande à Jean-Luc de
**prolonger, faire ressigner ou refuser** — sans rien décider à sa place. C'est la seule
feuille du produit où une décision de métier pourrait être perdue, donc c'est la seule où
l'écran écrit explicitement que rien n'a changé quand l'écriture échoue.

Elle **repose la question à chaque ouverture** tant que Jean-Luc n'a pas choisi (E8) : une
validité prolongée seule, sans signature, laisserait un prix tenir sans que personne
l'ait accepted.

Cette tranche porte **la démonstration « un devis produit le 28 du mois et expiré le 3 du
suivant »** de bout en bout. C'est ici que `page.clock` a un effet observable.

**Vague 7** (`index.impl_waves[7]`). Dépend de `F1`, `F2`, `F3`, `F8`, `S6`. Peut être
parallélisée avec `S7`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/app/echeance/types.ts
import { z } from 'zod';

// Trois issues, jamais deux, jamais une. B13 les énumère et interdit que
// l'application en applique une seule. C'est pourquoi ce n'est pas un
// `Bouton` unique avec un menu : ce sont TROIS blocs de 56 px, chacun avec
// sa conséquence écrite en dessous.
export const IssueEcheance = z.enum(['prolonger', 'faire_ressigner', 'refuser']);
export type IssueEcheance = z.infer<typeof IssueEcheance>;

// « Prolonger » exige une **durée explicite** : l'application ne prolonge pas
// d'elle-même. La liste est celle de B12, refermée par F2.
export const Prolongation = z.object({
  issue: z.literal('prolonger'),
  dureeValiditeJours: z.union([z.literal(15), z.literal(30), z.literal(60)]),
});

// Une nouvelle signature exige un nouvel `E17` valide : on ne « ressigne »
// pas par un bouton, on retourne sur `S7`.
export const Ressignage = z.object({ issue: z.literal('faire_ressigner') });

// Un refus est un fait : le devis ne peut plus partir. Il ne disparaît pas.
export const Refus = z.object({ issue: z.literal('refuser') });

export const DecisionEcheance = z.discriminatedUnion('issue', [
  Prolongation, Ressignage, Refus,
]);
export type DecisionEcheance = z.infer<typeof DecisionEcheance>;
```

### 2.2 Types et interfaces

```typescript
// apps/web/app/echeance/vue.ts

export type VueEcheance = {

  // sont affichées après une prolongation, sinon on ne sait pas ce qui a changé.
  dureeInitialeJours: 15 | 30 | 60;
  dureeEnCoursJours: 15 | 30 | 60;

```

### 2.3 Contrats API

Aucun : les trois décisions sont **locales**. Aucune ne demande le réseau, donc aucune ne
peut échouer pour cause de réseau — et c'est ce qui permet à `design-system.md`
d'affirmer que « la feuille fonctionne entièrement hors-ligne ».

## 3. Algorithmes critiques

### `termeDepuisDateEcriture` (couvre B12, E15, ADR-5)

```
termeDepuisDateEcriture(devis, sourceF2):
  # B12 : la validité court depuis la date ÉCRITE SUR LE DOCUMENT.
  # L'heure de l'ouverture, l'heure de l'envoi et l'heure de la découverte
  # n'entrent pas dans le calcul. E15 le dit : un devis retrouvé trois semaines
  # plus tard expire trois semaines plus tard, pas à la date du document + 30.
  return sourceF2.termeValidite({
    dateDocument: devis.date_document,          # ← la seule date qui compte
    dureeValiditeJours: devis.duree_validite_jours,
  })

# L'heure n'est lisible que par F2. `10-horloge.md` l'interdit ailleurs, et c'est
# ce qui rend la démonstration Playwright possible : `page.clock.install()`
# substitue `Date.now()`, et `Date.now()` n'existe QUE dans `packages/horloge`.
```

### `estExpire` (couvre B13)

```
estExpire(devis, sourceF2):
  return termeDepuisDateEcriture(devis, sourceF2).depassee
```

### `appliquer` (couvre B13, ADR-5 — le cœur de la tranche)

```
appliquer(devis, decision, sourceF2):
  # B13 : « elle ne prolonge pas seule, ne modifie aucun prix et ne signe rien
  # à la place de Jean-Luc ». Une seule des trois branches s'exécute, et
  # chacune est explicite.

  si decision.issue == 'prolonger' :
    # 1. La nouvelle durée est EXPLICITE et elle vient de la décision.
    # 2. NOUVEAU terme = terme + duree. Jamais `terme - delaiPaiementJours`,
    #    jamais une date lue ailleurs : c'est F2 qui fait l'arithmétique.
    # 3. Le PRIX ne bouge pas. `total_centimes` est relu après écriture et
    #    doit être identique — le test le vérifie.
    # 4. Si le devis était SIGNÉ et que la prolongation change le texte
    #    canonique, la signature TOMBE. B12 ne parle que de la durée, mais
    #    B11 parle de « modifier le devis », et la durée EST sur le document
    #    (« Valable 30 jours » est le slot `duree-validite` de EnTeteDevis).
    #    → le devis redevient À resigner, et l'écran le dit.
    écrire duree_validite_jours = decision.dureeValiditeJours
    …
    SI le devis était signé → invalider la signature (F4.invalider),
                               raison « signature annulée par une modification (B11) »
    return { terme: nouveauTerme, aResigner: etaitSigne }

  si decision.issue == 'faire_ressigner' :
    # NE MODIFIE AUCUN PRIX, NE PROLONGE AUCUNE DURÉE.
    # La seule chose produite est un devis non signé, qui doit repasser par S7.
    écrire aucune ligne métier ; marquer la signature comme needing-resign
    return { aResigner: true }

  si decision.issue == 'refuser' :
    # Un fait : le devis ne peut plus partir. Il n'est pas SUPPRIMÉ —
    # devise et facture ne sont pas supprimables (§ 4.14, gardes G8 et G10),
    # et il quitte le groupe 3 de S2.
    écrire sync_etat = 'refuse'
    return { termine: true }
```

**La phrase qui ferme la feuille** est écrite par le design et ne peut pas être retirée :
`Aucun de ces trois choix n'est fait pour vous. Aucun prix ne change sans que vous le
décidiez.` Elle est la manifestation à l'écran de B13.

### `reposerLaQuestion` (couvre E8)

```
# E8 : « le devis reste `expiré`, l'application le dit à chaque ouverture et
# repose la question ». Donc :
#
#   estExpire(devis)  ET  traiter(devis) == null  →  la feuille s'ouvre
#   estExpire(devis)  ET  traiter(devis) != null  →  la feuille NE s'ouvre PLUS
#
# Et il n'y a **aucun indicateur de « déjà vue »** : la question n'est pas
# posée une fois, elle est posée tant qu'elle n'a pas reçu de réponse. Un
# indicateur « vue » serait exactement « ne plus reposer la question », donc
# exactement la violation d'E8.
```

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| `terme` | feuille | **jamais stockée** : recalculée à chaque rendu par `F2` | au montage | quand `sourceF2` change, c'est-à-dire jamais |
| `dureeEnCoursJours` | document | `devis.duree_validite_jours` (colonne de F3) | à l'ouverture | à la prolongation |
| `traite` | document | `configuration`, clé `validite_de_signature_levee` (§ 4.7) plus l'état du devis | à l'ouverture | à la première issue appliquée |
| `issueChoisie` | composant | état local | à l'appui | au second appui |

**`terme` n'est pas stockée, et c'est tout le sujet de cette tranche.** Une date limite
stockée est une date limite qui a été calculée une fois, avec l'heure de ce moment-là, et
qui ne bouge plus : c'est exactement ce que la démonstration doit montrer qu'elle ne fait
pas.

## 7. Pièges à éviter

- **Prolonger tout seul, ou prolonger à 30 par défaut** — ⚠️ Ne pas étendre le terme sans
  une décision explicite. Le comportement correct (B13) est que « Prolonger » ouvre un
  `GroupeBoutons` et que **rien n'est écrit tant qu'aucune durée n'a été choisie**.

- **Réécrire la date limite à la date du jour** — ⚠️ Ne pas écrire
  `terme = aujourd'hui + duree`. Le comportement correct (B12, E15) est
  `terme = date_document + duree`, recalculé à chaque rendu par `F2`. Une date stockée
  ferait que le groupe 3 de `S2` ne se remplirait jamais tout seul.

- **N'appliquer qu'une issue sur trois** — ⚠️ Ne pas proposer « Refuser » seul, ni
  laisser un menu à trois entrées dont une seule serait réelle. Le comportement correct
  (`design-system.md` § 2 `LigneEcheance`) est **trois blocs de 56 px**, chacun avec sa
  conséquence écrite en dessous.

- **Marquer la question comme vue** — ⚠️ Ne pas écrire un `deja_vue` pour ne plus la
  reposer. Le comportement correct (E8) est l'inverse exact : la question est reposée à
  chaque ouverture tant qu'aucune issue n'a été appliquée.

- **Fermer la feuille quand l'écriture échoue** — ⚠️ Ne pas fermer et montrer un toast.
  Le comportement correct (`echeance.md` § 4) est que la feuille **ne se ferme pas** et
  écrit `Le devis n'a pas été modifié.` C'est le seul endroit du produit où une décision de
  métier pourrait être perdue.

- **Faire « ressigner » sans repasser par `S7`** — ⚠️ Ne pas écrire une fausse signature.
  Le comportement correct est que le devis redevient non signé et que la seule action
  possible est `Signer de nouveau`, qui ouvre `S7`.

## 10. Critères d'acceptation

- [ ] B12 : le terme d'un devis daté du `2026-03-28` est `2026-04-27` pour 30 jours, quelle que soit la date de la source `F2` — vérifié par deux sources opposées.
- [ ] B13 : chacune des trois issues laisse les deux autres inchangées, et le total est identique avant et après.
- [ ] B13 : `DecisionEcheance.parse({ issue: 'prolonger' })` lève sans durée explicite.
- [ ] B11 : prolonger un devis signé l'annule, avec la raison `signature annulée par une modification (B11)`.
- [ ] E8 : la feuille se rouvre à chaque ouverture tant qu'aucune issue n'a été appliquée ; après une issue, elle ne s'ouvre plus.
- [ ] E15 : retrouver un devis trois semaines plus tard ne change pas sa date limite.
- [ ] **R-10 : `page.clock` a un effet observable** — le rendu passe de `valide` à `expiré` quand l'horloge avance, sans qu'aucune action de l'utilisateur soit faite.
- [ ] `ddl-exec all` sort 0 et la garde `G12` est déclarée et refusée.
