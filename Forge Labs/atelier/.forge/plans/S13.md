## 1. Résumé de la slice

S13 choisit **une fois** la durée de validité par défaut — 15, 30 ou 60 jours, 30 par
défaut — et y trouve les deux exclusions que Forge ne fait pas, avec leur prix. Le défaut
est **écrit** au lieu d'être subi.

La règle qui porte la tranche : **un changement de durée ne s'applique qu'aux devis écrits
après**. Un devis déjà écrit garde sa durée, parce que sa date limite est derivée de la
date **écrite sur le document** (B12) et que cette date-là ne bouge pas.

**Vague 4** (`index.impl_waves[4]`). Dépend de `F1`, `F2`, `F3`, `F8`. Peut être
parallélisée avec `S1` et `S4`.

## 2. Contrats de données (code)

### 2.1 Schémas de validation

```typescript
// apps/web/app/reglages/duree.ts
import { z } from 'zod';

// La MÊME liste fermée que F2 et que `devis.duree_validite_jours`. Trois
// valeurs, et Zod refuse toute autre : 45 jours n'est pas une durée
// de validité de ce produit.
export const DureeValidite = z.union([
  z.literal(15), z.literal(30), z.literal(60),
]);
export type DureeValidite = z.infer<typeof DureeValidite>;

// La clé de configuration. Elle est dans la liste fermée du § 4.7 :
// `duree_validite_jours`, `assujetti_tva`, `taux_tva`, `taux_interet_retard`,
// `delai_relance_jours`, `validite_de_signature_levee`.
//
// `taux_tva`, `taux_interet_retard` et `delai_relance_jours` ont une valeur
// NON DÉCIDÉE (Q-006 et prd.md § 12). Elles sont donc ABSENTES de
// `configuration` tant que la décision n'est pas prise, et ce plan ne les
// écrit jamais : une valeur absente est un réglage jamais posé, ce qui est
// différent d'un réglage à `faux`.
export const CLE_DUREE = 'duree_validite_jours';
```

### 2.2 Types et interfaces

```typescript
// apps/web/app/reglages/types.ts

export type VueReglages = {
  // La durée par défaut. `30` quand rien n'est posé — jamais `undefined`.
  dureeDefaut: DureeValidite;
  // Vrai quand au moins un devis a déjà été écrit. C'est ce qui permet
  // d'écrire la règle au-dessus des boutons au lieu de la refuser en silence.
  devisEcrits: number;
  // Un devis a déjà été ENVOYÉ ? Alors sa durée est figée par la garde `G12`,
  // et l'écran doit le dire autrement que « ne s'applique qu'aux devis écrits
  // après ».

// Les deux exclusions, avec leur PRIX. Ce sont des faits du produit, pas des
// notes de bas de page : ils sont dans Réglages, en tête de liste.
export type Exclusion = {
  titre: string;
  prix: string;
  texte: string;
  source: 'contrat § 2' | 'prd.md § 9';
};
```

## 3. Algorithmes critiques

### `dureeParDefaut` (couvre B12)

```
dureeParDefaut(config):
  # B12 : « 30 jours par défaut ». Et § 4.7 : « Un réglage ABSENT est un
  # réglage jamais posed, ce qui est différent d'un réglage à `faux` ».
  v = config[CLE_DUREE]
  return DureeValidite.safeParse(v).success ? v : 30
```

### `changerDuree` (couvre B12, `G12`)

```
changerDuree(nouvelle, base):
  SI DureeValidite.safeParse(nouvelle).fail → REFUSER   # la liste est fermée

  # B12 : « Un changement de durée ne s'applique qu'aux devis écrits après ».
  # Donc ON N'ECRIT QUE LE REGLAGE. Aucun devis n'est touché, aucune ligne
  # `devis` n'est mise à jour, aucune empreinte ne change.
  #
  # C'est la phrase entière, et elle est le comportement : les devis déjà
  # écrits portent leur durée dans `devis.duree_validite_jours`, et cette
  # colonne est verrouillée après le premier envoi par le déclencheur
  # `devis_duree_fixee` (§ 4.14, garde `G12`).
  base.ecrireConfiguration(CLE_DUREE, String(nouvelle))

  # Et ce qui se produit à l'écran, c'est le fait, pas une confirmation :
  #   « La durée de validité par défaut est désormais 60 jours.
  #     Elle ne s'applique qu'aux devis écrits à partir de maintenant. »
```

### `regleApplicable` (couvre B12, US-8)

```
regleApplicable(devisEcrits, devisEnvoye):
  # Le texte affiché AU-DESSUS des boutons, et jamais un refus silencieux.
  SI devisEnvoye :
      # La durée de CE devis est figée pour toujours (G12). Le dire ici
      # évite que Jean-Luc tente de changer « pour le prochain » en croyant
      # que cela arreglera un devis déjà sorti.
      'La durée de validité est fixée avant le premier envoi. Elle ne bouge plus ensuite.'
  SINON SI devisEcrits > 0 :
      'La durée de validité est fixée avant le premier envoi. Elle ne s\'applique qu\'aux devis écrits après.'
  SINON :
      # Rien n'est écrit : la règle ne s'applique encore à rien, donc il
      # n'y a rien à écrire au-dessus de boutons actifs.
      null
```

## 7. Pièges à éviter

- **Appliquer la nouvelle durée aux devis déjà écrits** — ⚠️ Ne pas faire
  `UPDATE devis SET duree_validite_jours = … WHERE numero = …`. Le comportement correct
  (B12) est que **seul le réglage** est écrit : un devis porte sa durée dans sa propre
  ligne, et sa date limite court depuis sa date écrite.

- **Mettre une liste déroulante de durées** — ⚠️ Ne pas. Le comportement correct est
  **trois boutons** : la liste est fermée par B12, et une liste déroulante permettrait d'en
  choisir une quatrième.

- **Afficher `60 jours` sans `recommandé` sur `30 jours`** — ⚠️ Ne pas. Le comportement
  correct est que le défaut est **écrit** : `30 jours` porte `recommandé`, et le défaut
  existe au lieu d'être subi.

- **Refuser silencieusement un changement de durée** — ⚠️ Ne pas désactiver les boutons
  sans raison. Le comportement correct est la règle **écrite au-dessus** d'eux : un bouton
  désactivé sans raison est un bouton qui demande pourquoi.

- **Mettre le prix et les exclusions dans `configuration`** — ⚠️ Ne pas. Le comportement
  correct est qu'ils sont **écrits dans le code** : ce sont des faits du contrat, et une
  exclusion de contrat ne se modifie pas depuis un téléphone.

- **Ajouter une notification, un thème ou une langue** — ⚠️ Ne pas. Le comportement
  correct (B22, C2, `prd.md` § 7.4) est qu'il n'y en a pas, et que **cette absence** est
  ce que l'écran dit.

- **Écrire une valeur pour `taux_tva`, `taux_interet_retard` ou `delai_relance_jours`** —
  ⚠️ Ne pas, même une valeur « provisoire ». Le comportement correct (`prd.md` § 12,
  `architecture.md` § 4.7) est que ces trois clés restent **absentes** tant que Q-006 et le
  jour de la relance ne sont pas tranchés. Une valeur inventée devient une règle que l'agent
  appliquera avec l'autorité d'une règle et la fiabilité d'une supposition.

- **Faire dépendre l'écran du réseau** — ⚠️ Ne pas lire les exclusions depuis une API. Le
  comportement correct est qu'elles sont écrites dans l'application : cet écran n'a aucune
  dépendance réseau, donc il n'a rien à signaler.
