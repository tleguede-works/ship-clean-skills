## 1. Résumé de la slice

S6 montre le devis enregistré **tel qu'il sera imprimé** — total, date limite, état de sortie
et sa ligne de preuve — et dit ce qu'il reste à faire. C'est le sommet de la chaîne du
devis : toutes les autres tranches du module en dépendent.

L'ordre des trois lignes du pied est **une règle, pas un goût** :
**montant, échéance, état**. Le montant est la réponse à la question du client ; l'échéance
est la contrainte qu'il doit connaître ; l'état est ce qu'il dira au téléphone. Un écran
qui commence par l'état commence par le moins urgent et le plus facile à mal comprendre.

**Vague 6** (`index.impl_waves[6]`) : une seule tranche, sur le chemin critique.

Aucun nouveau schéma : S6 ne saisit rien de neuf. Il lit `devis`, `ligne_devis`,
`signature_devis` et la vue `devis_total`, tous déjà définis par `F3` et `packages/modele`.

### 2.2 Types et interfaces

```typescript
// apps/web/app/devis-detail/types.ts

export type VueDevis = {
  // L'identité du document. `date_document` est la date ÉCRITE : elle ne bouge
  // pas si le devis sort trois semaines plus tard (B12, E15).
  numero: string;
  client: { nom: string; adresse: string; courriel: string };
  date_document: string;
  duree_validite_jours: 15 | 30 | 60;

  lignes: LigneDevis[];
  total_centimes: number;             // la vue devis_total — ADR-8
  terme: DateLimite;                  // le type de F2, jamais un nombre de jours

  // Les trois emplacements de l'empreinte (§ 10.3). 1 et 2 sont des colonnes ;
  // 3 est le PDF et il est produit par F7.
  empreinte_courante: string | null;  // ce que le devis est MAINTENANT
  signature: SignatureCourante | null; // ce qu'il ÉTAIT au moment de la signer

  etatSortie: EtatSortie;             // les trois valeurs de F1
  preuve: PreuveSortie;               // les cinq variantes de F1
  signatureEtat: 'signature-absente' | 'a-resigner' | 'signe';
};

export type SignatureCourante = {
  empreinte: string;
  texte_canonique: string;            // l'archive de ce qui a été signé
  trace: string;                      // path SVG — AFFICHAGE seulement (C3)
  date_signee: string;
  heure_signee: string;               // 'HH:MM:SS', heure LOCALE (R-04)
  signataire: 'Jean-Luc';
  recu_le: string | null;             // horloge serveur, quand la ligne est partie
};
```

### 2.3 Contrats API

Aucun appel sortant. S6 lit le magasin local. Il affichera un `recu_le` **s'il est déjà là**
(la ligne est arrivée au serveur par `F6`), et il ne va **jamais** le chercher : le chercher
ferait dépendre l'affichage d'un document d'un réseau.

## 3. Algorithmes critiques

### `etatSignature` (couvre B11, E6, ADR-2)

```
etatSignature(devis, signature, empreinte_courante):
  # C'est LA comparaison des § 10.3, et elle est faite ici, à la lecture.
  si signature == null                                    → 'signature-absente'
  si signature.empreinte != empreinte_courante            → 'a-resigner'
  sinon                                                    → 'signe'
```

**`a-resigner` est un état de la ligne, pas un bandeau d'erreur.** Le tracé reste visible
et **barré**, la mention `À resigner` est dans l'en-tête, et le devis ne peut pas ressortir
avant une nouvelle signature (B11, E9/E6). Un devis `a-resigner` qui affiche `Envoyer` serait un
devis que le produit laisse sortir sans preuve.

### `piedDuDocument` (couvre B3, B5, B12)

```
piedDuDocument(v):
  # L'ORDRE EST UNE RÈGLE : montant, échéance, état.
  # montant  — la réponse à la question du client
  # échéance — la contrainte qu'il doit connaître
  # état     — ce qu'il dira au téléphone
  return [
    { slot: 'montant',        valeur: montantEnEuros(v.total_centimes) },
    { slot: 'devise',         valeur: 'euros' },
    { slot: 'ligne-echeance', valeur: ligneEcheance(v.terme) },      # F2
    { slot: 'mention-etat',   valeur: v.etatSortie },
    { slot: 'preuve',         valeur: v.preuve },
  ]
```

**Un seul total.** Il n'y a pas de « sous-total » et pas de « total TTC » à côté d'un
« total HT » : `design-system.md` § 2 `TotalBloc` le dit et B3 l'interdit.

### `etatSortieDepuis` (couvre B5, B6, B8, E3)

```
etatSortieDepuis(devis, service):
  # Les TROIS faits, et leur ordre compte : la confirmation passe avant la
  # déclaration, parce qu'un courriel confirmé est la preuve la plus forte.
  si devis.confirme_le != null        → ('confirme',    '2a')
  sinon si devis.date_declaree != null → ('declaration', '3a')
  sinon                                → ('attente',     preuveDepuis(devis, service.enLigne))

preuveDepuis(devis, enLigne):
  si devis.tentative_le != null → '1c'          # E3 : parti, sans retour
  sinon si enLigne             → '1a'
  sinon                         → '1b'
```

### `modifierSurDevisSigne` (couvre B11, ADR-2 — la transition qui compte)

```
modifierSurDevisSigne(devis, modification):
  # Tout ceci dans UNE transaction. ADR-2 : l'invalidation se produit à
  # l'ÉCRITURE, pas au moment de l'envoi.
  F3.dansTransaction(tx ⇒
      appliquer la modification
      recalculer devis.empreinte_courante = F5.empreinte(F5.texteCanonique(…))
      SI la nouvelle empreinte != signature.empreinte ALORS
          F4.invalider(file, devis.numero,
                       "signature annulée par une modification (B11)")
          marquer la signature comme 'annulee'
      FIN SI
  )
  # L'écran dit alors, immédiatement :
  #   « Ce devis a été modifié. Sa signature ne vaut plus rien.
  #     Il faut le faire signer de nouveau avant qu'il sorte. »
  # et le tracé de la signature est BARRÉ d'un filet --color-bordure-expire.
```

## 7. Pièges à éviter

- **Commencer le pied par l'état de sortie** — ⚠️ Ne pas inverser l'ordre. Le
  comportement correct (`design-system.md` § 2 `TotalBloc`) est **montant, échéance, état**,
  et l'ordre est une règle, pas un goût.

- **Afficher deux totaux** — ⚠️ Ne pas ajouter de sous-total ni de « total TTC ». Le
  comportement correct (B3) est un seul nombre, celui de `devis_total`.

- **Proposer `Envoyer` sur un devis `a-resigner`** — ⚠️ Ne pas rendre le bouton. Le
  comportement correct (B9, B11) est que le devis ne peut pas ressortir avant une nouvelle
  signature, donc l'action n'est pas « désactivée », elle **n'existe pas**.

- **Supprimer l'ancienne signature après une modification** — ⚠️ Ne pas faire de
  `DELETE` ni d'`UPDATE` sur `signature_devis`. Le comportement correct (`30-empreinte.md`)
  est que la ligne est **immuable** — le déclencheur `signature_preuve_gele` refuse les
  deux — et que l'annulation est un **état** porté par la comparaison des empreintes, pas
  une suppression. Un historique qu'on peut réécrire n'est pas une preuve.

- **Faire de l'annulation un toast** — ⚠️ Ne pas afficher une alerte qui disparaît. Le
  comportement correct est un `BandeauMessage` `avertissement` **persistant** et un tracé
  **barré** : Jean-Luc doit voir que la signature a sauté quand il rouvre l'écran dans une
  heure.

- **Transformer `Envoyer` en `Réessayer` hors ligne** — ⚠️ Ne pas le faire. Le
  comportement correct (`design-system.md` § 6) est que le bouton **reste visible** et
  passe à `desactive` : un devis écrit et non envoyé n'a pas échoué, il n'a pas été envoyé.

- **Afficher un devis vierge quand le devis est introuvable** — ⚠️ Ne pas rendre un devis
  vide. Le comportement correct est `BandeauMessage` `echec` avec la raison complète : un
  devis à zéro euros ressemble à un devis réel.

- [ ] `design-system.md` § 2 `TotalBloc` : les trois lignes du pied sont dans l'ordre montant, échéance, état, et **un seul** total est rendu.
- [ ] B3 : le montant affiché et le montant du texte canonique sont le **même entier**.

- [ ] Hors ligne : `Envoyer` reste visible en `aria-disabled`, `Signer` reste actif, la preuve passe de `1a` à `1b`.
