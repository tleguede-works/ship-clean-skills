## 1. Résumé de la slice

F3 est **le seul endroit par où une écriture passe**. Toute écriture de l'application —
client, devis, ligne, signature, réglage, déclaration de sortie — entre par
`dansTransaction`, dans une transaction, et **renvoie le rang obtenu**. Ce rang est
l'ordre de sortie de la file d'attente : il est monotone, local, et ne dépend d'aucune
horloge.

Le magasin vit dans SQLite compilé sur OPFS, dans un **Web Worker**, et il pose **le même
schéma que le serveur** moins les déclencheurs `plpgsql` (§ 4.15), plus la table
`rang_sequentiel` et le déclencheur `rang_suivant`. Un seul modèle, deux magasins,
différenciés par une liste de colonnes (§ 4.0) : c'est ADR-7.

**Vague 1** (`index.impl_waves[1]`). Dépend de `F2` (l'horloge) et de `F5` (l'empreinte,
parce que `empreinte_courante` se recalcule à chaque écriture). Seize sommets en dépendent,
dont quatorze tranches : c'est **le socle de données** du projet (§ 6.3).

## 2. Contrats de données (code)

### 2.1 Schémas de validation

F3 ne *valide* pas : il **transpose**. Les schémas Zod vivent dans `packages/modele/` et
sont portés par les tranches qui possèdent des entités. Ce que F3 pose, c'est le DDL de
`architecture.md` § 4.15, transposé en SQLite :

```sql
-- apps/web/magasin/schema.sql — le MÊME modèle que le serveur (§ 4.0),
-- moins les fonctions LANGUAGE plpgsql, plus rang_sequentiel et rang_suivant.

PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = FULL;   -- prd.md § 7.2 : une coupure ne perd rien

-- Les tables du § 4.14, dans l'ordre du document : une clé étrangère qui
-- référence une table pas encore créée échoue à la création, pas à l'écriture.
--   client, devis, ligne_devis, signature_devis, envoi_courriel, sortie_devis,
--   configuration, facture, ligne_facture, relance
-- MODIFIÉES PAR RAPPORT AU § 4.14, et uniquement par cela :
--   * `devis.rang_entree`   devient `NOT NULL DEFAULT 0`  (colonne d'appareil)
--   * `devis.jeton_tentative`, `devis.tentative_le`, `devis.sync_etat` : conservées
--   * `signature_devis.recu_le`, `envoi_courriel.demande_le|confirme_le|refuse_par`,
--     `sortie_devis.sortie_id`, `facture.emise_le` : ABSENTES (horloge serveur)
--   * les déclencheurs `signature_preuve_gele`, `envoi_confirmation_monotone`,
--     `facture_emise_gelee`, `ligne_facture_gelee`, `facture_bloquee_tant_que_incomplete`,
--     `devis_duree_fixee` : ABSENTS (garanties d'archive, § 4.0)
--   * les vues `devis_total` et `facture_total` : PRÉSENTES, même expression que § 4.13

CREATE TABLE rang_sequentiel (
  id      smallint PRIMARY KEY CHECK (id = 1),
  dernier bigint NOT NULL DEFAULT 0
);
INSERT INTO rang_sequentiel (id, dernier) VALUES (1, 0);

-- Le rang est compté par le magasin, jamais par l'appelant (F3).
CREATE TRIGGER rang_suivant
  AFTER INSERT ON devis
  FOR EACH ROW WHEN NEW.rang_entree = 0
  BEGIN
    UPDATE rang_sequentiel SET dernier = dernier + 1 WHERE id = 1;
    UPDATE devis SET rang_entree = (SELECT dernier FROM rang_sequentiel WHERE id = 1)
      WHERE numero = NEW.numero;
  END;
```

**La liste de colonnes de la § 4.0 est la seule différence autorisée entre les deux
magasins.** Elle est vérifiable ligne à ligne, et c'est pour cela qu'elle est écrite en
commentaire dans le fichier : un contrôle peut la relire, un relecteur peut la compter.

### 2.2 Types et interfaces

```typescript
// apps/web/magasin/types.ts

// `ecrire` renvoie TOUJOURS le rang obtenu. C'est ce qui permet à une écriture
// d'entrer dans la file sans que personne ne soit prié de calculer un rang.
export type Tx = {
  ecrire<T>(req: (tx: Tx) => T): Promise<{ valeur: T; rang: number }>;
  lire<T>(req: (tx: Tx) => T): Promise<T>;
};

export type MagasinLocal = {
  dansTransaction<T>(fn: (tx: Tx) => Promise<T>): Promise<T>;
  prochainRang(): Promise<number>;
  // La persistance est demandée au système, et son refus est remonté :
  // prd.md § 7.2 dit que les données écrites ne peuvent pas être effacées
  // sans que Jean-Luc en soit informé. R-05.
  persistant(): Promise<boolean>;
  fermer(): Promise<void>;
};

// Une écriture de devis, en une seule transaction. C'est le SEUL endroit où
// `empreinte_courante` est recalculée (§ 10.3, point 1).
export type EcrireDevis = {
  numero: string;
  client_id: string;
  date_document: string;
  duree_validite_jours: number;
  lignes: { rang_ligne: number; designation: string; quantite_centimes: number;
            prix_unitaire_centimes: number; montant_centimes: number }[];
  jeton_tentative?: string | null;
};

// Ce qu'une écriture de devis rend, et que F4 consomme.
export type DevisEcrit = {
  numero: string;
  rang: number;                 // rang monotone, jamais l'heure
  total_centimes: number;       // la vue devis_total, ADR-8
  empreinte_courante: string;   // recalculée par F5, jamais lue
};
```

### 2.3 Contrats API

Aucun : F3 ne parle à personne. Il n'a **aucun** client HTTP, et c'est vérifiable :
`grep -rn 'fetch' apps/web/magasin/` doit rendre **zéro**. Un magasin local qui
appelle le réseau n'est plus un magasin local, et la démonstration hors ligne s'appuie
sur cette absence.

## 3. Algorithmes critiques

### `dansTransaction` (couvre B4, E2)

```
dansTransaction(fn):
  ouvrir (ou réutiliser) la transaction      # journal_mode = WAL, synchronous = FULL
  BEGIN IMMEDIATE
  rang_depart = prochainRang()              # lu dans la transaction, pas avant
  valeur = await fn(tx)
  COMMIT                                      # si fn lève : ROLLBACK, et rien n'est écrit
  return valeur

prochainRang():
  SELECT dernier FROM rang_sequentiel WHERE id = 1     # + 1 si INSERT imminent
```

Trois propriétés, chacune avec sa raison :

| Propriété | Raison |
|---|---|
| `BEGIN IMMEDIATE` | Le rang doit être strictly monotone. En `DEFERRED`, deux transactions concurrentes lisent le même `dernier` et obtiennent le même rang. |
| `synchronous = FULL` | E2 : une coupure de réseau — ou une coupure de courant — ne perd aucune donnée déjà saisie. `NORMAL` peut perdre la dernière transaction. |
| `ROLLBACK` sur exception | Un devis à moitié écrit est pire qu'un devis absent : il apparaît dans une liste et il ne peut pas être relu. |

### `ecrireDevis` (couvre B1, B3, B12, ADR-8)

Une seule transaction, dans cet ordre, et cet ordre est une règle :

```
ecrireDevis(d):
  1. vérifier B1 : nom du client non vide, date_document présente,
     au moins une ligne.   → sinon refus, ÉCRITURE ANNULÉE
  2. client = lire ou créer le dossier client (recherche exacte par nom,
     jamais « créer un nouveau dossier » en doublon : E14 veut deux dossiers,
     pas un dossier et un devis orphelin)
  3. INSERT devis (numero, client_id, date_document, duree_validite_jours,
                   rang_entree = 0, sync_etat = 'écrit ici')
       → le déclencheur rang_suivant attribue le rang
  4. INSERT ligne_devis pour chaque ligne, dans l'ordre de rang_ligne
       → la contrainte ligne_montant_calcule refuse un montant qui ne vaut pas
         round(quantite × prix_unitaire_centimes)
  5. total = SELECT total_centimes FROM devis_total WHERE numero = …
       → la VUE, ADR-8 : il n'existe pas de colonne où écrire un total
  6. UPDATE devis SET empreinte_courante = await empreinte(
       texteCanonique({ numero, date_document, client, lignes, total_centimes }))
       → § 10.3 point 1 : l'empreinte de ce que le devis est MAINTENANT
  7. renvoyer { numero, rang, total_centimes, empreinte_courante }
```

**L'étape 5 ne peut pas écrire.** Une vue n'a pas de point d'écriture, et c'est pour
cela qu'elle est une vue : la garde `G1` de `architecture.md` § 4.14 tente d'écrire un
total et échoue, et c'est la seule preuve possible d'une contrainte absente.

### `persistant` (couvre § 7.2, R-05)

```
persistant():
  si navigator.storage?.persisted existe :
    return await navigator.storage.persisted()
  return await navigator.storage.persist()    # et son refus est remonté à l'écran
```

Un refus n'est pas une erreur : c'est un fait que l'interface doit dire. La réponse du
produit n'est alors pas une promesse, c'est le compteur permanent (B23) et le partage en
un geste.

## 4. Plan composants

### 4.1 Arbre de composants

F3 ne produit aucun composant React : c'est un magasin. Le seul composant qui le consomme
directement est `FileAttente` (F4) et l'adaptateur de `F8` qui lit le compteur.

```
apps/web/magasin/
├─ schema.sql          le DDL du § 4.15, transposé
├─ worker.ts           le Worker : ouvre OPFS, tient la connexion, sert les requêtes
├─ protocole.ts        les types de messages Worker ↔ page
├─ client.ts           la façade côté page : MagasinLocal
├─ ecritures.ts        ecrireDevis, ecrireClient, ecrireSignature, ecrireSortie…
├─ ecritures.test.ts   les propriétés de transaction, de rang et de total
└─ coherence.test.ts   la § 4.0 : le schéma de l'appareil == celui du serveur, à la colonne
```

### 4.2 Composants

| Composant | Type | Fichier cible | Props | State | Événements |
|---|---|---|---|---|---|
| — | — | Aucun. Le magasin ne rend rien ; il publie des valeurs que `F8` lit. | — | — | — |

### 4.3 États par écran

Aucun écran ne lit le magasin directement. `Suivi`, `devis-lignes` et `dossier-client`
reçoivent leurs données du magasin Zustand de `F8`, alimenté par `F3`. Un écran qui
appelle `F3` lui-même aurait deux chemins de lecture, donc deux vérités.

### 4.4 Formulaires

Aucun formulaire n'écrit dans F3 sans passer par `dansTransaction`. Le formulaire de
`S5` (lignes de devis) valide **une ligne** par transaction : c'est ce qui rend E2
tenable, une coupure entre deux lignes ne perd que la ligne en cours de frappe.

## 5. Gestion d'état

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Documents, lignes, signatures, réglages, file | appareil | SQLite sur OPFS | à la première ouverture du schéma | par `dansTransaction` uniquement |
| `rang_sequentiel.dernier` | appareil | la table elle-même | `0` à la création du schéma | par le déclencheur `rang_suivant` |
| Connexion SQLite | `Worker` | variable du Worker | au démarrage, **une seule fois** | jamais (R-09) |
| Compteur de non-envoyés, connectivité | globale | magasin Zustand de `F8` | au démarrage de l'application | par `F8`, sur ordre de `F3` |

**Une seule instance, ouverte au démarrage, jamais par écran** (R-09). L'application ne
rend rien tant qu'elle n'est pas ouverte : `ListeDevis` n'a pas d'état de chargement
animé, donc le magasin doit être prêt avant le premier rendu.

## 6. Traçabilité des règles

### 6.1 Règles métier (B*)

| ID | Règle (PRD) | Implémentée où | Approche |
|---|---|---|---|
| B1 | Un devis porte identifiant, date, nom de client et au moins une ligne | § 3 `ecrireDevis` étape 1 | refus **avant** tout `INSERT`, pas de devis à moitié écrit |
| B3 | Le total affiché, imprimé et signé est le même nombre | § 3 étape 5, vue `devis_total` (ADR-8) | une seule expression `SUM(montant_centimes)` dans tout le produit |
| B4 | Un devis est écrit sur l'appareil avant toute action vers l'extérieur ; une coupure ne perd rien | `dansTransaction`, `synchronous = FULL` | aucune écriture ne sort de `F3` ; la vérification est `grep fetch` vide |
| B12 | La durée de validité est fixée avant le premier envoi | `duree_validite_jours` écrit à la création, `IN (15,30,60)` | le déclencheur `devis_duree_fixee` est une garantie d'archive ; sur l'appareil c'est `F3` qui refuse la réécriture |
| B21 | Un dossier client regroupe tous ses devis | `client_id` sur `devis` et `facture` | la cascade n'existe que sur `ligne_devis` : un dossier survit à ses devis |

### 6.2 Edge cases (E*)

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| E1 | Le devis se fait dans une cave, sans réseau | aucune requête réseau dans `apps/web/magasin/` ; la boucle entière est locale | `grep -rn 'fetch' apps/web/magasin/` rend 0 |
| E2 | Le réseau tombe au milieu de la saisie | `synchronous = FULL` ; une ligne = une transaction | `ecritures.test.ts`, propriété « fermer le Worker au milieu d'une écriture ne laisse pas de ligne partielle » |
| E10 | L'appareil est perdu avec des devis non envoyés | `persistant()` et son refus remonté ; rien ne promet une seconde copie | `R-05` |
| E14 | Deux devis pour le même client le même jour | `client` n'a pas d'unicité sur `nom` ; deux devis = deux numéros | `§ 4.1`, contrainte `client.nom` sans `UNIQUE` |
| E15 | Un devis retrouvé trois semaines plus tard | rien à faire : `date_document` est une colonne, pas un calcul | `devis.date_document` |

| ID | Contrainte (PRD) | Comment elle est respectée |

## 7. Pièges à éviter

- **Laisser l'appelant fournir le rang** — ⚠️ Ne pas écrire
  `INSERT INTO devis (…, rang_entree) VALUES (?, …, Date.now())`. Le comportement
  correct (`20-ecriture-locale.md`, ADR-1) est que le rang est attribué par le
  déclencheur `rang_suivant` à partir de `rang_sequentiel`, et que l'appelant écrit `0`.

- **Oublier `BEGIN IMMEDIATE`** — ⚠️ Ne pas laisser SQLite choisir le mode. Le
  comportement correct est `BEGIN IMMEDIATE`, sinon deux écritures concurrentes lisent le
  même `dernier` et obtiennent le **même rang** — ce qui rend la file triable par
  horodatage sans que personne ne l'ait décidé.

- **Poser une colonne `total_centimes`** — ⚠️ Ne pas ajouter la colonne « pour éviter la
  jointure ». Le comportement correct (ADR-8) est la vue `devis_total` : une vue n'a pas
  de point d'écriture, et la garde `G1` tente d'écrire et échoue.

- **Laisser `synchronous` à sa valeur par défaut** — ⚠️ Ne pas écrire
  `PRAGMA synchronous = NORMAL` « pour aller plus vite ». Le comportement correct
  (E2, `prd.md` § 7.2) est `FULL` : la performance d'un devis unique ne vaut pas la
  perte de la dernière transaction.

- **Ouvrir la base par écran** — ⚠️ Ne pas appeler `ouvrir()` depuis chaque route. Le
  comportement correct (R-09) est une instance unique au démarrage, et l'application ne
  rend rien avant.

- **Copier le DDL `plpgsql` dans SQLite** — ⚠️ Ne pas porter
  `signature_preuve_gele` ou `facture_emise_gelee` sur l'appareil. Le comportement
  correct (§ 4.0) est que ces garanties sont d'**archive**, et que sur l'appareil la
  même garantie vient de `F3` + `F4` + le fait que l'appareil n'envoie qu'il ne fusionne
  (ADR-3).
